# 会话管理系统方案

> 这份文档解决一件事：**用户开了一个对话，要能存下来、能翻回去、能在上面继续**（类似豆包 / 墨刀的历史对话）。
>
> 现状是会话状态全在内存里，页面一刷新就没了。这份文档给出存储选型、数据模型、接口设计和改造清单。
>
> **实施状态：P0-P3 已完成（存储底座 / 落库打通 / 接口 + 侧栏 / 恢复会话），P4 项目管理、P5 安全与多 worker 待做。** 实现记录见 `05_功能盘点_按状态机.md` 的「会话管理系统」小节。
>
> 阅读顺序：部署形态 → 存储选型 → 数据模型 → 接口 → 改造清单 → 实施顺序 → 风险。
>
> 关联文档：`05_功能盘点_按状态机.md`（状态机各节点现状）、`06_ReAct改造方案.md` §6.2（SessionStore 设计草案）、`01_接口协议.md`（接口字段口径）。

## 1. 背景与目标

**要做的事**：

| 能力 | 说明 |
| --- | --- |
| 会话列表 | 侧边栏列出历史对话，显示标题、最后更新时间、消息数 |
| 新建会话 | 点「新建对话」开一条空白会话 |
| 恢复会话 | 点历史会话，完整还原当时的对话内容、状态机位置和右侧报表预览 |
| 继续对话 | 恢复后能接着聊，状态机从上次的位置继续推进 |
| 会话管理 | 改标题、删除、归到某个项目下 |
| 项目管理 | 项目列表增删改查，会话归属项目 |

**明确不做**（本期）：

- 不做多用户 / 登录 / 租户隔离（当前是单用户本地工具）。
- 不做会话全文检索（先按标题 + 项目过滤，够用）。
- 不做跨设备同步（数据在服务端，天然共享；但本期不做云端部署）。

## 2. 关键约束与现状

### 2.1 现在什么都没有持久化

后端四个内存字典，进程一重启全丢：

| 服务 | 位置 | 键 | 重启后 |
| --- | --- | --- | --- |
| `AgentService._pending_choices` | `app/services/agent_service.py:100` | `conversationId` | 丢失 |
| `TemplatePreviewFlow._sessions` | `app/services/template_preview_flow.py:40` | `conversationId` | 丢失 |
| `DefinitionSaveService._store` | `app/services/definition_save_service.py:34` | `definitionId` | 丢失 |
| `PreviewService._store` | `app/services/preview_service.py:46` | `reportRunId` | 丢失 |

全仓搜索 `sqlite|SQLAlchemy|redis` **零命中**，`requirements.txt` 只有 8 行，没有数据库依赖。唯一持久化的是日志文件 `~/Library/Logs/haewu-ai-report/backend.log`。

### 2.2 会话身份和状态都握在前端手里

- `conversationId` 前端生成：`workbench.js:11`（`"conv_" + Date.now()`）、`workbench.js:115`（停止后换新）、`workbench.js:1467`（清空后重置）。**后端从不生成也不校验**，schema 里就是裸的 `str`（`app/schemas/agent.py:143`）。
- 状态机 `state` 前端持有，每次请求带上。后端只校验转移合法性（`agent_service.py:509-526`），无法独立重建会话位置。
- 草稿 `reportDefinition` 存在前端 `session.definition`，靠 `snapshots` 字段来回传。
- AgentScope Agent 每请求新建（`agentscope_report_agent.py:84-94`），跨轮记忆必须靠外部注入。

### 2.3 现有的「恢复」能力是假的

`workbench.js:106-107` 的 `pendingResume` 只在页面内存里，刷新即丢。`resumeOfConversationId` 只进日志（`routers/agent.py:45`、`:87`），没有任何业务消费。

### 2.4 现成的设计草案

`06_ReAct改造方案.md` §6.2 已经定义了 SessionStore 的字段结构（`routeHistory` / `collectedInfo` / `pendingPlan` / `currentDraft` / `clarificationCount` / `fixLoopCount`），但代码里没有对应实现。

**结论**：会话管理系统就是这个 SessionStore 的**持久化宿主 + 历史列表 UI**。两者应该一起设计，不要各做各的。

## 3. 部署形态：本地虚拟服务器，数据存哪

这是本次最需要先讲清楚的一件事。

### 3.1 「没有服务器」的实际含义

现在跑的 `uvicorn app.main:app` **本身就是服务器**，只是绑在 `127.0.0.1:8000`，只有本机能访问。三个部署形态的关系是：

```
                  ┌─────────────────────────────────────┐
浏览器 ──HTTP──▶  │  FastAPI (uvicorn)                  │
                  │    ├── SQLite 文件（数据在本机磁盘）   │
                  └──▲──────────────────────────────────┘
                     │
              ┌──────┴──────┐
              │             │
        localhost 直连   Cloudflare Tunnel
        （本机访问）      （公网访问，手机/别的电脑也能开）
```

**要澄清的关键点**：Cloudflare Tunnel **只解决「谁能访问到进程」，不解决「数据存在哪」**。用了 Tunnel，数据依然在本机 SQLite 文件里。Tunnel 是条隧道，不是台服务器。

所以「上 Cloudflare」和「历史对话存哪」是两个独立问题，各有各的答案：

| 问题 | 答案 |
| --- | --- |
| 谁能访问 | localhost（只有本机）或 Cloudflare Tunnel（公网，可选） |
| 数据存在哪 | 后端 SQLite 文件，**跟部署形态无关**，永远在本机 |

Tunnel 的真正价值是：手机、另一台电脑、或者同事访问时，看到的是**同一份历史对话**（因为数据在同一个后端进程里），而不是各自浏览器的一份。这是好事。

### 3.2 三种形态对比

| 形态 | 启动方式 | 谁能访问 | 数据位置 | 适合阶段 |
| --- | --- | --- | --- | --- |
| A. 纯本地 | `uvicorn app.main:app --port 8000` | 只有本机 | 本机 SQLite | **当前推荐**，日常开发 |
| B. 本地 + Tunnel | A + `cloudflared tunnel --url http://localhost:8000` | 公网（拿到链接的人） | 本机 SQLite | 需要给别人演示 / 手机上试 |
| C. 云端 | 真服务器 + Postgres/D1 | 公网 | 云端 | 正式上线时再做 |

### 3.3 形态 B 的安全前提（必须注意）

当前后端**没有任何鉴权**，CORS 是 `allow_origins=["*"]`（`app/main.py:29-35`）。一旦挂到公网 Tunnel：

- 任何拿到链接的人都能读走全部历史对话；
- 能调 `/api/agent/chat` 消耗你的火山方舟 API Key 额度；
- 能读到本地 mock 数据里的授权范围。

所以形态 B **必须**配一个访问控制。最小成本做法（本期一起做）：

1. `.env` 里加 `AI_ACCESS_TOKEN`（本地开发留空 = 不校验，仅限 localhost）；
2. 前端启动时读 `?token=` 或让用户输入，存 `sessionStorage`，之后每个请求带 `X-Access-Token` 头；
3. 后端加一个 `Depends` 依赖做校验，非空 token 时才生效。

这一条不写进方案就等于把内网数据裸奔到公网。

## 4. 存储选型

### 4.1 对比

| 方案 | 新增依赖 | 跨设备 | 并发写 | 迁移到云端 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 前端 localStorage | 无 | 否，浏览器一清就没 | 无所谓 | 无后端真相源，后端 Agent 读不到历史 | ❌ 只适合做缓存 |
| JSON 文件 | 无 | 否（后端持有文件才行） | 覆盖写有竞态 | 要重写一遍 | ❌ |
| **SQLite** | **零**（`sqlite3` 是标准库） | 是（后端统一读写） | WAL 模式可读写并行 | SQL 方言接近 Postgres，改连接层即可 | ✅ **推荐** |
| PostgreSQL（Docker） | 装库 + 驱动 | 是 | 好 | 无需迁 | ❌ 现阶段太重，且违背「不能上服务器」 |
| Cloudflare D1 | wrangler + 账号 + CI | 是 | 好 | 无需迁 | ❌ 现阶段没有账号链路 |

### 4.2 为什么是 SQLite

1. **零新增依赖**。Python 标准库自带 `sqlite3`，`requirements.txt` 一行不用改。这是现阶段最大的实际收益。
2. **单文件，可直接搬**。`backend/data/haewu.db` 拷走就是全量数据，备份 = `cp`。
3. **比内存字典强在多 worker**。现在 `uvicorn --workers 4` 会让四个进程各有一份内存字典，`_pending_choices` 直接分裂。换成 SQLite 后不管几个 worker 都共享一份真相。
4. **迁移路径干净**。所有 SQL 走 Repository 抽象层，将来换 Postgres / D1 只换实现不改调用方。
5. **不违背「不能上服务器」**。它就是一个本地文件。

### 4.3 落点与配置

| 项 | 值 |
| --- | --- |
| 默认路径 | `backend/data/haewu.db` |
| 环境变量 | `AI_SESSION_DB_PATH`（沿用 `AI_BACKEND_LOG_PATH` 的先例，`app/logging_config.py:18-21`） |
| 连接参数 | `PRAGMA journal_mode=WAL`（读写不互斥）、`busy_timeout=5000`、`foreign_keys=ON` |
| 访问方式 | `sqlite3.connect(path, check_same_thread=False)`；FastAPI 路由**写成同步 `def` 而不是 `async def`**，让 FastAPI 自动丢到线程池，不阻塞 event loop |
| 备份 | 停服后拷文件，或用 `sqlite3 haewu.db ".backup out.db"` |

### 4.4 目录结构

```text
backend/
  app/
    storage/
      __init__.py
      base.py            # SessionRepository 抽象协议（Protocol/ABC）
      sqlite_store.py    # SqliteSessionRepository 实现
      models.py          # dataclass: WorkspaceRecord / SessionRecord / MessageRecord
    services/
      session_service.py # 业务编排：建会话、记消息、列表、恢复快照
    routers/
      sessions.py        # /api/sessions + /api/workspaces
  data/
    haewu.db             # 运行时生成，加进 .gitignore
```

`app/storage/base.py` 定义协议，是为了让将来换 Postgres 时只写 `postgres_store.py`，`session_service.py` 一行不动。

## 5. 数据模型

### 5.1 先分清三个 id（最容易搞混的地方）

| id | 谁生成 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| `sessionId` | **后端**（`POST /api/sessions`） | 一条对话从建到删，**永不改变** | 数据库主键、侧边栏列表、恢复入口 |
| `conversationId` | 前端（现状不动） | 一次请求线程；**停止生成时会换新** | 后端日志追踪、隔离迟到响应 |
| `resumeOfConversationId` | 前端（现状不动） | 指向被中断的那次请求 | 日志关联、重放去重 |

**为什么必须分开**：`workbench.js:114-115` 在用户点「停止」后会换新 `conversationId`，目的是隔离已经发往后端但来不及终止的模型响应。如果数据库按 `conversationId` 建会话行，**一次停止就会把一个对话劈成两条历史记录**——用户看到侧边栏里同一个对话出现两次。

`sessionId` 与 `conversationId` 是两个正交的东西，不冲突：`sessionId` 是「哪条对话」，`conversationId` 是「哪次请求线程」。前端两个都带着走即可。

### 5.2 表结构

```sql
-- 项目（侧边栏「历史项目」分组）
CREATE TABLE IF NOT EXISTS workspaces (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    subject_ref TEXT,               -- 可选：默认 subjectRef，绑定业务范围
    subject_id  TEXT,               -- 可选：默认 subjectId
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

-- 会话（= 一次对话 = 一个 sessionId）
CREATE TABLE IF NOT EXISTS sessions (
    id                   TEXT PRIMARY KEY,      -- sess_xxx，后端生成，永不变
    workspace_id         TEXT REFERENCES workspaces(id) ON DELETE SET NULL,
    title                TEXT NOT NULL DEFAULT '新对话',
    state                TEXT NOT NULL,         -- 当前状态机节点，恢复时回填
    design_session_id    TEXT,
    report_definition_id TEXT,
    preview_run_id       TEXT,
    message_count        INTEGER NOT NULL DEFAULT 0,
    snapshot             TEXT,                  -- JSON：草稿/预览等现场
    created_at           TEXT NOT NULL,
    updated_at           TEXT NOT NULL,
    deleted_at           TEXT                    -- 软删
);

-- 消息（一条 user 或 assistant 气泡）
CREATE TABLE IF NOT EXISTS messages (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    seq           INTEGER NOT NULL,              -- 会话内序号，从 1 开始
    role          TEXT NOT NULL,                 -- user / assistant
    content       TEXT NOT NULL DEFAULT '',      -- 纯文本气泡
    payload       TEXT,                          -- JSON：questions/blocks/changeSet/options
    client_msg_id TEXT,                          -- 客户端消息 id，用于幂等去重
    created_at    TEXT NOT NULL,
    UNIQUE(session_id, seq),
    UNIQUE(session_id, client_msg_id)
);

CREATE INDEX IF NOT EXISTS idx_sessions_updated ON sessions(updated_at DESC);
CREATE INDEX IF NOT EXISTS idx_sessions_ws      ON sessions(workspace_id);
CREATE INDEX IF NOT EXISTS idx_messages_session ON messages(session_id, seq);
```

`UNIQUE(session_id, client_msg_id)` 是幂等写的关键，见 §5.4。

### 5.3 两个命名坑（必须避开）

| 坑 | 说明 | 规避 |
| --- | --- | --- |
| `projectId` 撞名 | 现有 `context.projectId`（如 `project_001`）是**业务项目 ID**，跟侧边栏的「历史项目」不是一回事 | 新概念代码里一律叫 `workspace`，界面文案叫「历史项目」 |
| `state` 语义 | 前端请求里的 `state` 是「请求发起时的状态」，后端存的 `state` 是「上次响应后的状态」 | 恢复一律以服务端为准；后端存的是「上次响应后的 state」，天然更准 |

### 5.4 消息落库规则（最容易做错的地方）

**规则一：user + assistant 成对写，且都在请求成功完成后写。**

```
POST /api/agent/chat/stream
  → AgentService.chat() 返回 AgentResponse
  → router 拿到 response 后：
       1. upsert session（state = response.state，更新 title / message_count / updated_at）
       2. insert message(role=user,      content=用户实际输入)
       3. insert message(role=assistant, content=response.reply, payload=结构化部分)
  → 再发 SSE 事件
```

**为什么不在请求入口就写 user 消息**：被中断的请求（「停止」）如果已经写了 user 消息，恢复出来的历史就会留下一条没有回复的孤儿消息。改成成对写，被中断的请求什么都不留，历史干净。

**规则二：`__advance__` 不作为 user 消息入库。**

节点 6-11 靠前端反复发 `__advance__` 触发自动推进（`workbench.js:90`、`agent_service.py:65` 的 `ADVANCE_MESSAGE`）。这是内部控制消息，用户从没输入过。它的 assistant 回复（如「草稿已保存，接下来进入校验」「正在校验报表定义…」）**要入库**，因为那是用户真实看到的进度文案。

判断依据用后端已有的常量 `ADVANCE_MESSAGE`，不要硬编码字符串。

**规则三：user 消息只存「用户实际输入」。**

前端 `sendMessage` 里 `visibleText` 才是用户看到并输入的原文；`text` 可能被替换成 `pendingResume.body.message`（重发场景）。落库用 `visibleText` 的语义，但**重发场景要靠幂等键去重**，见下。

**规则四：用 `client_msg_id` 保证幂等。**

「继续工作」重发时，前端重发的是**原始那条消息**（`workbench.js:755`）。这时有两个竞态：

- 原请求已被中断、什么都没写 → 重发写一条，正确；
- 原请求在后端已经跑完并写了，但前端刚好 abort 掉没收到 → 重发会再写一条，**重复**。

光靠 `resumeOfConversationId` 判断不可靠（它只能说明「这是一次重发」，不能说明「原消息是否已落库」）。

可靠做法：前端给每条用户消息生成一个 `messageId`（同一轮重发时**复用同一个** id），后端按 `(session_id, client_msg_id)` upsert。重复到达时覆盖而不是新增。

这条幂等键顺带把网络重试、双击发送一并解决了，成本只是多一个字段和一个唯一索引。

**规则五：Debug Trace 不入库。**

它是前端根据 SSE 事件渲染的调试信息，落库会让库快速膨胀且没有读取价值。

### 5.5 `snapshot` 存什么

恢复会话要还原右侧报表预览，光有消息不够，得把现场一起存：

```json
{
  "definition": { "...ReportDefinitionDraft..." },
  "policy":     { "...ReportPolicyDraft..." },
  "lastReportRun": { "reportRunId": "run_x", "status": "SUCCEEDED" },
  "previewPayload": { "...GET /api/report/preview/{runId} 的返回..." },
  "editingTargetRegionId": null
}
```

`previewPayload` 直接缓存一份的原因：`PreviewService._store` 是内存的（`preview_service.py:46`），后端重启后 `GET /api/report/preview/{runId}` 会 404，右侧图表就空了。缓存一份就不依赖内存态。

**选择锁 `lockedChoice` 不放 snapshot**，由后端 `sessions.pending_choice` 列权威提供（见 §6.3）。

体积估算：单条 snapshot 几十 KB，SQLite 存这个量级毫无压力。

## 6. 接口设计

新增两个 router 前缀：`/api/sessions`、`/api/workspaces`。`/api/agent/chat` **只新增两个可选字段**，现有字段语义一个都不改。

> 字段口径的**唯一真相源在 `01_接口协议.md` §12**（已随 P0-P3 补齐）；下表是摘要，冲突时以接口协议为准。

### 6.1 会话

| 方法 | 路径 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- | --- |
| POST | `/api/sessions` | `{ title?, workspaceId? }` | `{ sessionId, title, state, createdAt }` | **后端生成 `sessionId`**；**不建库行**，避免侧边栏出现空会话 |
| GET | `/api/sessions` | `?workspaceId=&q=&limit=50&offset=0` | `{ items: [...], total }` | 列表，按 `updated_at` 倒序，不含软删、不含空会话 |
| GET | `/api/sessions/{sessionId}` | — | `{ sessionId, title, state, messages[], snapshot, pendingChoice, ... }` | 详情，含全部消息（恢复用） |
| PATCH | `/api/sessions/{sessionId}` | `{ title?, workspaceId? }` | `{ sessionId, title, workspaceId }` | 改标题 / 换项目 |
| DELETE | `/api/sessions/{sessionId}` | — | `204` | 软删（写 `deleted_at`） |

列表项字段：`sessionId` / `title` / `state` / `messageCount` / `workspaceId` / `createdAt` / `updatedAt`。

**空会话不建行**：`POST /api/sessions` 只铸 id。库行在第一轮请求成功完成时随消息一起创建。这样侧边栏不会堆积空条目，也不会有孤儿行。

### 6.2 项目

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/workspaces` | 项目列表，附每个项目的会话数 |
| POST | `/api/workspaces` | 建项目 `{ name, description?, subjectRef?, subjectId? }` |
| PATCH | `/api/workspaces/{id}` | 改名 / 改描述 |
| DELETE | `/api/workspaces/{id}` | 删项目，其下会话 `workspace_id` 置 NULL（不删会话） |

### 6.3 与现有 `/api/agent/chat` 的衔接

**新增两个可选字段**（向后兼容，老前端不传也能跑）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `sessionId` | `str \| None = None` | 会话 id。不传时后端回退用 `conversationId` 当会话 key（等价于「一条请求一个会话」的旧行为） |
| `messageId` | `str \| None = None` | 本条用户消息 id，用于幂等去重。不传时退化为「不幂等，每次都新增」 |

后端解析会话 key 的顺序：

```python
session_id = request.sessionId or request.conversationId
```

`resumeOfConversationId` 保持现有语义（日志关联），另外兼作重放标记：**请求带 `resumeOfConversationId` 时，说明这是一次重放**，此时若 `messageId` 与库里已有的一致则覆盖、不新增。

**`pendingChoice` 由后端权威提供**。原本的 `_pending_choices` 内存字典按 `conversationId` 存，现已删除，改由 `sessions.pending_choice` 列按 `sessionId` 存（这样停止生成、换新 conversationId 也不会丢选择锁）。`GET /api/sessions/{sessionId}` 直接把它带出来，前端恢复时据此重建输入锁定。

> 实现补充：`pendingChoice` 的结构是 `{ state, question }`；用户选定提交后锁被清空（写 `null`）。恢复时回放出来的 `question` 是新对象，判定必须按 `question.id` 比对，不能用对象引用。

**选择锁的三条实现纪律（2026-10-22 补充）**

1. **回放必须把下拉框画出来**。`replayAssistantMessage()` 的每个分支都要跟当场路径对齐——`USER_EDITING_TEMPLATE` 分支原先漏了 `appendConfirmActions`，恢复后页面只剩一段文字，但 `restoreSession` 又按 `pendingChoice` 把输入锁死，于是变成「输入框锁死、却没有一个能点的下拉框」。回放时统一传 `{ lock: false }`：画出选项，不抢占当前输入锁。
2. **同名下拉框取最后一个**。`syncInputControls()` 原来用 `findIndex` 按 `data-question-id` 找 enable 哪个 select，页面出现多个同 id select 时（每一轮编辑都画一个）会 enable 最早那个、disable 当前轮那个，用户点当前轮的下拉框就是灰的。改成倒序遍历取**最后一个**——那才是当前轮刚画的。
3. **缺选项时不要抢锁**。`appendConfirmActions()` / `appendReadyActions()` 在 question 缺失或 `options` 为空时，原先会 `setChoiceLock({ options: [] })` 写一把空锁；`syncInputControls()` 判断 `!lockedChoice?.options?.length` 为真，就把页面上**所有**已有 select 全部 disable。现在缺选项时只提示、不抢锁，锁是给「真的有选项可选」的场景用的。

回归流程：`flows/session-dropdown-restore.flow.json`（断言恢复后存在 enabled 的 select、且该 select options > 1）、`flows/session-nav.flow.json` 第 3 条（恢复后选下拉继续对话）。

> 注：`session-dropdown-restore.flow.json` 原来依赖库里一条历史遗留的「你好」会话，那条会话的后端追问是自由文本（`selectionOnly=false`），根本没有下拉框，流程必然失败。已改成流程自己新建一条「生成 A 机房昨日能耗日报」会话再恢复，不再依赖库里的历史数据。

**编辑入口的可见性跟着状态走（2026-10-22 补充）**

右侧预览区的「展示方式 / 粒度 / 删除」和标题直接编辑，只在用户于下拉菜单选了「修改」之后才开放；没选之前右侧是只读的。

- 判定：`isEditingEnabled()` = `session.state === "USER_EDITING_TEMPLATE"` **且** `!lockedChoice`。第二个条件是必要的——编辑到一半后端又弹出「同意 / 修改 / 重新开始」时输入被锁住，此时编辑按钮显示了也点不动。
- 落地方式：编辑入口收进 `.region-tools` 容器，标题能否直接改用 `contenteditable` 属性，两者都由 `syncPreviewEditability()` 统一同步；显隐用 CSS 类 `#preview-root.preview-editable`，不需要重画整块预览。
- 触发同步的时机：`setState()`（状态机位置变了）、`setChoiceLock()` / `clearChoiceLock()`（选择锁变了）、`renderPreview()` 末尾兜底。

回归流程：`flows/preview-edit-tools.flow.json`（断言草稿态编辑入口不可见、选「修改」后可见且 `contenteditable=true`）。

| # | 还原项 | 来源 | 漏了会怎样 |
| --- | --- | --- | --- |
| 1 | 对话气泡（用户 / 助手） | `messages[]` | 对话区空白 |

| 3 | 右侧报表预览（ECharts / KPI / 表格） | `snapshot.definition` + `snapshot.previewPayload` | 右栏空白 |
| 4 | 状态机 `state` | `sessions.state` → `session.state` | 状态徽标错、下一步动作错 |
| 5 | 选择锁 `lockedChoice` | `GET /api/sessions/{id}` 返回的 `pendingChoice` | 后端要求选选项、前端却放行自由文本，前后端不一致 |

| 7 | `pendingResume`（停止后续跑） | 后端按 `resumeOfConversationId` 重放时不需要；跨会话恢复时不还原 | 「继续工作」在刷新后失效 |

| 方案原设计 | 实际实现 | 原因 |
| --- | --- | --- |

新建对话与停止的行为边界：生成期间（请求在跑或还有自动推进定时器）**不允许切走会话界面**——「新建对话」「点历史会话」两条路径统一提示「请先停止正在生成的请求」并拒绝切换。拦截只挡界面切换，不掐断在途请求：请求继续跑完、正常落库，历史里留得住，用户看到的仍是同一个会话。点击「停止」则中断该请求，不保存未完成的半截对话。页面关闭、网络断开也可能取消尚未完成的请求，不承诺断线后继续生成。

## 10. 风险与边界

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| **Tunnel 暴露无鉴权** | 当前 CORS `*` + 无鉴权，公开后历史对话和 API Key 都危险 | 形态 B 必须配 `AI_ACCESS_TOKEN`；或只用 localhost |
| **会话被停止操作劈成两条** | `conversationId` 停止时换新（`workbench.js:115`），若按它建库行会分裂 | 引入独立 `sessionId`，停止时只换 `conversationId` |
| **重放导致消息重复** | 「继续工作」重发原始消息，可能与已落库的重复 | `client_msg_id` 幂等 upsert |
| **`__advance__` 污染历史** | 自动推进是内部控制消息，不是用户输入 | 跳过 `ADVANCE_MESSAGE` 的 user 消息，保留其 assistant 回复 |
| **多 worker 下内存态分裂** | `_pending_choices` / `_sessions` / `_store` 都是进程内字典 | 全部落库；或阶段内固定 `--workers 1` |
| **`state` 双写漂移** | 前端带 state、后端也存 state，异常中断时可能不一致 | 恢复一律以服务端为准；后端存的是「上次响应后的 state」，天然更准 |
| **消息体积膨胀** | 长对话 + 大 ChangeSet | 现阶段不设限；后续按会话保留最近 N 条 + 归档 |
| **预览缓存失效** | `previewPayload` 是快照，Mock 数据变了不会自动更新 | 明确它是「当时那张图」，用户点「重新生成」即刷新 |
| **前端 localStorage 缓存** | 列表数据缓存到 localStorage 能秒开 | 可选优化，但**服务端是唯一真相源**，缓存失效以服务端为准 |
| **`sqlite3` 阻塞 event loop** | 同步调用在 async 路由里会卡住 | 路由写同步 `def`，交给 FastAPI 线程池；或后续换 `aiosqlite` |
| **协议新增两个字段** | `sessionId` / `messageId` 是新增而非修改 | 均为可选，老前端不传时行为等价于旧逻辑；已在 `01_接口协议.md` v1.1 补口径 |
| **和 `06_ReAct改造方案.md` §6.2 冲突** | 两边都定义会话态结构 | 本文档的 `snapshot` 字段就是 §6.2 SessionStore 的落地形态，实现时以 §6.2 的字段名为准 |
