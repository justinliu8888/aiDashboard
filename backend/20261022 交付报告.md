## 留给集成 Agent 的接线点
1. `app/schemas/agent.py` ：`AgentRequestContext` 加`visibleRegionIds: list[str] | None = None` （前端已按此名发送）。
2. `app/schemas/agent.py` ：`AgentResponseDomainObjects` 加`pendingEditPlan` ，字段`planId / draftRevision / targetRegionId / operations / summary` （可选`unverified` ）。
3. `app/services/agent_service.py` ：改为「先产候选计划 → 下发 pendingEditPlan → 收到「接受修改」后校验 revision 再原子应用」；「继续调整 / 取消」清掉待决计划；规则的快路径也要走确认菜单，不要再先 apply 再让用户确认旧草稿。
4. 前端不会自行应用计划，`accept` 的判定与草稿写入全部在后端；前端只发中文文本，后端从 Agent D 的会话存储取待确认计划。
5. 字段名若与前端不一致，只改 workbench.js 的`EDIT_PLAN_CONTRACT` 一处常量即可（读侧已有别名兼容）。
## 已知限制
- 读侧对 plan 字段做了别名兼容（`planId/plan_id/id` 等），若后端用完全不同的命名，需要在`EDIT_PLAN_CONTRACT` 里补别名。
- 「未验证能力」只在计划顶层或操作项里带`unverified/limitations/notes` 之类键时才会显示，后端不传就不显示。
- 前端只判断「草稿版本不一致」这一种过期依据；若后端在草稿版本不变时也要作废旧计划，需要后端自己标脏并把计划摘掉。
- 旧的「同意 / 修改 / 重新开始」菜单路径原样保留；只有响应里出现`pendingEditPlan` 时才切换到新菜单，两套不会同时出现。
- 现有`preview-edit-tools.flow.json` 、`session-dropdown-restore.flow.json` 依赖 8000 端口的后端服务，本次未运行（会写共享 SQLite），但改动不触及它们的断言路径。
