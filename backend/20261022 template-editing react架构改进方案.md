# Template Editing ReAct 架构改进方案

> 访谈日期：2026-10-22
>
> 范围：`USER_EDITING_TEMPLATE`，即已有报表草稿后的问答、澄清与编辑。
>
> 状态：访谈决定已逐题确认；本文记录目标和轻量版范围，不表示代码已按本文实现，也不表示真实数据编译已经接通。
>
> 背景方案：[06_ReAct改造方案.md](./06_ReAct改造方案.md) 的节点 5.5。

## 一、为什么要改

用户在编辑模版时说“删除第三个”，希望 Agent 结合**当前页面可见的卡片顺序**找到候选对象，报出名称并请用户确认，而不是要求用户重新提供“具体区块和修改内容”。用户问“这个数据能按哪些粒度编译”，希望它先查当前草稿、数据源和能力，回答可选粒度；如果进一步要求改成分钟趋势，才形成修改计划。

当前反复出现的“暂时无法查证这项修改，请补充具体区块和修改内容后重试”，并不能证明用户没说清楚。这句话是编辑态业务 Agent 没拿到可用结论时的统一降级文案；模型初始化、执行、解析或提交失败等均可能触发，单凭两句用户输入无法认定具体故障分支。规则也有局限：它不按页面顺序理解“第三个”，会把“哪些粒度”中的词当成编辑线索；“昨天下午”还可能被缩成“昨天”整天。

因此，本次不是把所有话都交给模型猜，而是让规则处理确定的表达，让 ReAct 在不确定时查事实、给具体选项，并将最终修改交给确定性代码校验和执行。

## 二、访谈如何收敛

| 轮次 | 讨论焦点 | 用户确认的结论 |
| --- | --- | --- |
| Q1–Q3 | 查询还是修改；“第三个”；追问底线 | 查询也留在编辑语境中；删除先定位可见对象并确认；同一项修改最多追问三轮，仍不明确则说明卡点，不随便生成或修改。 |
| Q4–Q6 | 探索性话术；不支持的能力；轮次范围 | 只有明确提出修改才可能改草稿；能力不足时先查证、解释和给可行替代，不简单断言“数据不存在”；三轮按同一项待定修改计，新需求重新计数。 |
| Q7–Q9 | “昨天下午”、阶段范围、分钟数据源 | 不暗定下午的时间范围；先打通轻量编辑链路，不冒充真实编译；可提议换到有权限且指标兼容的分钟源，指标口径变化须先说明并确认。 |
| Q10–Q11 | 时间歧义和轻量版验收 | “昨天下午”给具体时间范围选项并追问，用户已给出具体时间则不重复问；第一阶段要有可验证的回答、具体追问及受控草稿修改，不只留下空框架。 |
| Q12–Q14 | 公司 Skill 中台、本地复用、页面顺序 | 这里的 Skill 是公司中台的能力单元，可以由 Python 实现并封装为 Tool，**不是 Trae IDE 的 `SKILL.md`**；当前只在本地复现契约，先复用已有 Tool；编辑态问答需要不修改草稿的独立结论；序号按客户看到的正文卡片算。 |
| Q15–Q17 | 建议与授权、技术失败、过期目标 | Agent 有把握时先给修改摘要和下拉菜单，客户明确点“接受”才修改；“赶紧改”也不跳过确认；工具/模型故障不计入用户澄清轮次；确认前草稿顺序或版本变化须重新核对。 |
| Q18–Q20 | 确认范围、置信度、菜单内容 | 所有编辑态修改都先确认，包括规则快路径；第一版暂用模型自报 `confidence` 控制“给确认菜单或继续追问”，阈值和可靠性打问号；摘要具体写出修改内容、数据源、粒度/时间窗及未验证能力，菜单提供“接受修改 / 继续调整 / 取消”。 |
| Q21–Q23 | 执行护栏、规则速度、组合修改 | 点击接受后仍做确定性目标/权限/字段/粒度校验，不额外轮询模型；明确的规则计划直接给确认菜单，不为取得 `confidence` 再调模型；换源加改粒度作为一次确认、一次原子修改，要么都成功，要么都不写。 |

访谈中曾以“昨天下午自动定义为 14:00–18:00”举例，**最终决定不是采用这一默认值**，而是让用户选择或明确具体时间；不能把早期讨论中的举例写成已确认规则。

## 三、目标交互与职责边界

```text
用户输入 + 当前草稿/页面上下文
  → 判断本轮是探索性查询，还是明确的修改请求
  → 规则能确定的走规则快路径；否则在编辑模式下由 ReAct 查草稿、目录、指标和能力
  ├─ 查询：回答查证结果，可提出修改建议；不修改草稿
  ├─ 缺事实或偏好：给当前对象相关的具体选项，最多追问三轮
  ├─ 技术故障：说明查证失败并允许重试；不当作用户缺参
  └─ 可行修改：提交候选计划 → 展示摘要和确认菜单
                                   → 用户接受 → 确定性校验与原子应用 → 更新草稿
                                   → 用户调整/取消 → 原草稿不变
```

- **理解和规划用 ReAct，执行不交给模型。** 模型可以理解指代、组合意图和候选解释；数据源、粒度、时间窗、权限及目标都要通过工具或确定性代码校验。模型自报信心只影响交互节奏，不能越权执行。
- **查询与修改分开收尾。** “有哪些粒度”应回答实际查到的能力并可建议怎样修改；“改成分钟级”才产生待确认的修改计划。回答结束不应假造一个 `EditPlan`。
- **确认对象可核对。** “第三个”按前端可见的正文卡片顺序，不把后台可能包含的隐藏标题区计入；确认中同时给出卡片名称和修改摘要。待确认计划关联草稿版本；草稿变动后不沿用旧序号直接执行。
- **确认不等于保存。** 点击“接受修改”只更新当前草稿；最终保存仍走原有确认/保存流程。强制下拉选择期间保持选项锁，不能通过自由文本绕过。
- **能力不足不等于一概拒绝。** 先查授权范围内是否有可替代的源、粒度或时间窗；没有可验证的路径时解释实际卡点，不宣称已经编译或预览成功。

## 四、与现有架构怎么衔接

这里所说的“理解时间、查可用数据源、提出修改计划”是三个**中台 Skill 职责**，不是要求立即新建三个 Trae Markdown Skill。公司中台代码库当前不在本项目中；本地 `app/tools/` 以统一契约模拟未来的能力接入，`registry.export_manifest()` 可导出上架清单。接入真实中台时需要验证其实际协议，不能假设现有 Mock 已经代表生产能力。

第一阶段优先复用：

| 职责 | 本地已有能力 | 轻量版需要补齐 |
| --- | --- | --- |
| 读当前对象与查数源 | `get_current_draft`、`get_current_region`、`search_catalog`、`search_metric`、`check_capability` | 指代和页面可见顺序的映射；授权、口径和候选来源明确展示。 |
| 理解时间 | `TemplateEditEngine` 的时间规则和草稿 `timeWindow` | “昨天下午”等非完整窗口不能被规则截成“昨天”；先追问具体时间，再规范化时间窗。 |
| 提交候选修改 | `submit_edit_plan`、`TemplateEditEngine.apply()` | 修改前的待确认计划、摘要和草稿版本绑定；接受后校验；支持换源加改粒度的原子组合。 |
| 回答编辑态问题 | 已有事实查询工具，但编辑态没有独立的只回答结论 | 增加不修改草稿的结构化回答路径，允许附可行修改建议。 |

现有 `EditPlan` 只含一个 `intent`、一个 `target`、一个 `operation`；`apply()` 一次只分派一种意图。测试中的“先换源再改分钟粒度”是两次 `apply()`，**不是**一次原子计划。要实现 Q23，不能只改 Prompt：需以最小范围补组合计划/确定性原子应用，失败不留半成品。

## 五、第一阶段验收话术

| 输入场景 | 期望行为 |
| --- | --- |
| “这个数据能按哪些粒度编译？” | 从当前对象定位授权数据源，回答实际登记的可用粒度和限制，可附修改建议；不生成 ChangeSet。指代不唯一时点名候选再问。 |
| “删除第三个” | 按可见正文卡片列出第三张的名称及删除摘要，给确认菜单；未接受不删除，草稿改变须重新核对。 |
| “改成昨天下午” | 不静默写入整日“昨天”；询问具体时间段，确认后展示精确窗口摘要，再走修改确认。 |
| “把小时趋势排名改成分钟趋势排名” | 查当前源及有权限的分钟源、指标口径和字段兼容性；必要时提议换源与改粒度的一次组合修改；确认后原子应用，失败不写半项。 |
| “赶紧开始改吧” | 可以减少无意义解释，但仍展示待确认的具体修改摘要和选项，不视为点击接受。 |
| 工具超时、无授权结果、模型无可用结论 | 区分技术故障和用户缺参；保留原草稿，说明查证失败或授权范围不足并给下一步，不重复泛泛要求“补充区块和修改内容”。 |

验收至少覆盖规则快路径、ReAct 查证、问答不修改、三轮具体追问、确认/拒绝、草稿版本变化、组合修改失败回滚。以上是**目标用例**，不是现有测试通过声明。

## 六、明确不做与待验证

- 第一阶段不做任意自然语言生成 SQL 的通用编译器，不把“AI 理解了时间/粒度”说成“实际数据已按该条件取出”。
- 当前 `preview_service.py` 使用固定 Mock 快照，趋势预览未按区块粒度和时间窗重新取数；真实编译、数据服务和预览接入单独推进。`2HOUR` 也不是当前能力枚举支持的粒度，不能仅凭小时数据可聚合就声称已经支持“两小时趋势”。
- **待验证：模型自报 `confidence` 的阈值及可靠性。** 第一版不为信心评估增加额外模型轮询；需要记录误判案例，后续再决定是否调整阈值或增加更客观的就绪判断。无论信心多高，点击接受后仍必须通过确定性校验。
- **待实现：编辑态跨轮待确认计划及三轮计数的会话化。** 现有消息与部分选择态可持久化，但并没有独立的待决计划和同一修改的澄清计数；技术失败不计入三轮，新请求重新计数。
- 现有静态代码核对不等于真实模型链路验收；固定降级文案的具体生产触发原因仍需在可复现请求和日志下定位。

## 八、五个写代码 Agent 如何并行

参照 [《AI 辅助开发的 7 个阶段》“阶段六：执行”](../../../日常提升认知/ai%20hero%20by%20matt%20pocock/think%20like%20AI%20engineer/深度好文%20-%20AI辅助开发的7个阶段.md#L112-L119) 的思路：不是把同一条调用链硬拆给五个人同时修改，而是先确定依赖和接口，让**没有文件冲突的工单同时开工**，最后再集成。以下是建议的五条并行工作线；它们仍围绕同一个业务 Agent，不是要上线五个业务 Agent，也不是立即建五个中台 Skill。

### 8.1 开工前的共同约定（短暂串行，无需 Git）

1. **直接使用同一个本地目录。** 五个 Agent 都读取和修改当前工作区，现有后端/前端代码（包括本地工具实现）即为共同起点，不要求提交、建分支或建 worktree。开工前只需确认大家看到的是当前文件；为防误改，可选择在工作目录外另存一份普通文件备份，但不以此阻塞开发，不覆盖现有改动。
2. **先冻结最小接口，不预先实现。** 五人约定同一份待确认计划含计划 ID、草稿 revision、目标 region、操作列表和面向用户的摘要；确认选择只有“接受 / 继续调整 / 取消”；只回答的结论不带修改操作；前端向后端传递**可见正文卡片 ID 的顺序**。字段名、请求/响应样例在开工前定一次。这里是工作契约建议，非声称现有 API 已具备这些字段。
3. **同目录按文件独占认领。** 每个 Agent 只修改表中归自己负责的文件；未认领的共用文件先不改。发现必须跨界时告诉集成负责人并登记待接线点，不能多人同时保存同一个文件。各 Agent 先拿到本方案、冻结后的样例及各自的验收用例。

### 8.2 第一波：五人同时写

| Agent / 工单 | 独占修改范围 | 做到什么、交付什么 | 明确不碰 |
| --- | --- | --- | --- |
| **A：编辑态 ReAct 与回答能力** | `app/agents/agentscope_report_agent.py`、`app/agents/prompts/template_edit.md`、`app/tools/submit_edit_answer_tool.py`（按约定的新文件名）、`app/tools/registry.py`、`app/tools/schemas.py`、`tests/test_tools.py`、相关 Agent 单测 | 让编辑态能查草稿/目录/能力后**回答而不改草稿**，或给出含自报 `confidence` 的候选编辑；低信心给具体追问，工具/模型故障给技术失败而非用户缺参。新 Tool 遵守现有中台清单契约和节点白名单。用假工具结果单测，不等真实中台。 | 不改 `agent_service.py`、编辑引擎、会话存储、前端。暂不自己直接应用候选计划。 |
| **B：时间与可见对象解析** | 独立的纯解析模块（例如 `app/services/edit_time_resolver.py`、`app/services/edit_reference_resolver.py`）及独立新测试文件 | 输入原话、逻辑时间/时区、当前草稿和前端可见 ID 顺序，输出明确目标/时间窗或**需要追问的候选**。“昨天下午”不得降格成整天；“第三个”不得把隐藏标题区算进去。先提供可调用函数与单测，交由集成阶段接入规则快路径。 | 不改 `template_edit_engine.py`、`workbench.js`、`agent_service.py`；不自行发明下午的默认起止时间。 |
| **C：组合修改与确定性校验** | `app/schemas/edit_plan.py`、`app/services/template_edit_engine.py`、`tests/test_template_editing.py` | 在冻结的计划接口下支持一个 region 的“换源 + 改粒度”组合；在临时草稿上验证目标、权限、字段和粒度，全部通过才提交新草稿及 ChangeSet，失败原草稿不变。保留现有单项规则/单项编辑行为。 | 不改 Agent Prompt、Tool 注册、会话存储、前端；不接真实取数编译器。 |
| **D：待确认计划与三轮状态** | `app/services/session_service.py`、`app/storage/sqlite_store.py`、`app/schemas/session.py`、`tests/test_session_store.py` 及独立状态单测 | 按冻结契约保存/回读待确认计划、草稿 revision 和针对**同一修改**的澄清次数；接受前校验计划是否过期，调整/取消清理待决计划；技术故障不计三轮，新需求重新计数。复用现有选择态存储，避免平行造第二套真相。 | 不改 `agent_service.py`、AgentScope、编辑引擎、前端；不把模型内存当跨轮存储。 |
| **E：客户可见的确认交互** | `../frontend/pages/workbench.js`、`../frontend/pages/workbench.html` 和归自己所有的前端交互流程文件 | 根据冻结的响应样例展示具体修改摘要、来源/粒度/时间窗说明和“接受 / 继续调整 / 取消”选项；按正文卡片可见顺序提供 ID；必选下拉期间锁住自由文本与发送按钮，收到迟到/过期响应不误改界面。先用约定样例做 UI 冒烟，不等后端集成。 | 不改后端 API、Agent Prompt、编辑引擎。不能自行改动请求/响应字段名。 |

**并行条件：** A、B、C、D、E 在接口样例和文件认领固定后可直接在同一个本地目录同时开工；每人只写自己的文件和专属测试。尤其不要安排两个人同时改 `template_edit_engine.py`、`agentscope_report_agent.py` 或 `workbench.js`。不要同时运行会改写同一 SQLite 数据库、共用生成物或服务端口的测试/开发服务，也不要对整个项目批量格式化；并发期间某项全量测试失败须先分清是否因为别的 Agent 尚未接线。前端改动需按项目规则跑静态自检；交互按钮改动还需跑交互冒烟并查看截图。

### 8.3 第二波：单人集成，不与第一波抢文件

第一波各自完成认领文件和针对性单测后，再指定**一名集成 Agent**接管共用编排文件，主要是 `app/services/agent_service.py`、必要的 `app/schemas/agent.py`、API/状态机测试，以及第一波交付的接口适配。这个角色可以由五人中的一人转任，但须等其他 Agent 停止改这些关联文件；集成阶段再统一跑全量测试和端到端验证。

集成顺序建议：

```text
共享本地目录 + 冻结请求/响应样例 + 文件认领
              ↓
  A（Agent/Tool） ∥ B（解析器） ∥ C（编辑引擎） ∥ D（会话） ∥ E（前端）
              ↓
  集成 Agent：规则/问答分流 → 待确认计划 → 接受后原子应用 → 前端联调
              ↓
  全链路验收与缺陷回流；真实数据编译/预览仍是后续独立工单
```

集成时把 B 的解析结果接到规则和 Agent 输入，把 A 的“只回答/候选计划”接入服务层，把 C 的原子应用放在**D 校验待确认计划和草稿版本之后**；E 只消费统一 API。规则明确时直接生成待确认计划，不为取得模型信心额外调模型。最后验证“问粒度不改草稿”“删可见第三张需确认”“昨天下午先问”“换源加分钟粒度一次确认且失败不写半项”“模型故障不占追问轮次”“不跳过确认”等用例。

**交付门槛：** 每个 Agent 报告自己改了哪些文件、针对性测试结果、尚未接线处及已知限制；集成 Agent 负责跨模块测试、回归和实际模型对话，不需要分支合并。当前实现仍是 Mock 数据与 Mock 预览，即便五条工作线和集成都完成，也不能把真实数据编译/预览标记为完成。
