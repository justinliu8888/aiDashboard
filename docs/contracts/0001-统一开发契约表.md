## 0. 这张表怎么用

### 0.1 六要素

规格第 76 条要求每项都写清六件事。本表每一节都用同一张表写这六件事，顺序固定：

| 六要素 | 含义 |
| --- | --- |
| **字段位置与类型** | 落在哪个模块的哪个对象、字段名、类型、取值域 |
| **候选与生效语义** | 这一项有没有「候选 / 生效」之分，谁覆盖谁 |
| **是否持久化** | 落不落库、落在哪张表 / 哪个字段 |
| **旧数据的默认行为** | 老会话、老定义、老记录没有这一项时按什么算 |
| **生产者与消费者** | 谁写、谁读 |
| **版本校验方式** | 怎么比大小、怎么判过期、冲突了怎么办 |

### 0.2 标注约定

| 标注 | 含义 |
| --- | --- |
| **既有** | 当前 `feature/unified-report-generation` 代码里已有这个字段或结构，位置与类型照抄 |
| **既有（语义扩展）** | 位置和类型已有，但取值域或语义在本轮扩展；既有取值继续有效 |
| **本轮新增** | 当前代码里没有，由本轮 10 张票实现 |

字段名约定：JSON 载荷与 API 一律用 **camelCase**（照 `planId` / `planRevision` /
`draftRevision` / `metricRef` / `fieldRef` / `sourceRef` / `selectionOnly` 的既有惯例）；
Python 侧内部常量用 `UPPER_SNAKE`。

**本轮定名**：规格给了语义但没给确切字段名的地方，本表直接定名并在正文标注
「本轮定名」。下游票按本表的名字写代码，不要另起名字。

### 0.3 改动契约的规矩

本表**随代码维护**，与代码同仓同分支。改动契约必须：

1. 改字段位置、字段名、取值域、默认值 → 契约表版本号**必须升位**（见 0.4）；
2. 每次改动都要在 §10 变更记录里追加一行，写清**受影响的消费方**（哪个模块、哪张票）；
3. 受影响的消费方**必须**在同一轮改动里同步，否则该票的产物按旧契约工作即为返工；
4. 只改措辞、不改语义 → 记为补丁版本（`v1.0.1`），也要在 §10 写一行。

「受影响的消费方」在本表 §9 有索引，改动前先查 §9。

### 0.4 版本号规则

`主版本.次版本.修订号`：

| 位 | 何时加 |
| --- | --- |
| 主版本 | 字段位置、字段名、取值域、默认值发生**不兼容**变化 |
| 次版本 | 新增字段或新增概念，老数据按 §各节「旧数据的默认行为」补默认值 |
| 修订号 | 只改措辞与错别字，不动语义 |

兼容规则：本轮 10 张票内，老数据一律**不迁移、不删除**（规格 Out of Scope 11），
新增字段按各节的默认值兜底。

## 1. 数据来源模式（sourceMode）

### 1.1 字段

| 字段 | 位置 | 类型 | 取值 | 现状 |
| --- | --- | --- | --- | --- |
| `sourceMode` | `ReportDefinitionDraft.metadata.sourceMode` | `str` | `"simulated"` \| `"user_json"` | 本轮新增 |
| `sourceMode` | `region.templateBinding.sourceMode` | `str \| None` | 同上；`None` = 继承定义级 | 本轮新增 |
| `sourceMode` | `region.templateBinding.previewSpec.sourceMode` | `str` | 同上；**区域级预览描述里的那一处**（写于 `template_definition_service` 的转换层） | 本轮新增 |
| `sourceMode` | `regions[].payload.sourceMode`（区域渲染载荷） | `str` | 同上 | 本轮新增 |
| `dataSource` | `regions[].payload.dataSource` | `str` | `"simulated"`（由模拟造数器产出）\| `"user_json"`（由用户粘贴并经服务端校验的记录数组产出） | 既有（`"simulated"` 语义**不动**）；**`"user_json"` 本轮新增**（#64） |
| `dataSource` / `dataSourceLabel` | `TemplateRegion.dataSource` / `.dataSourceLabel` | `str \| None` | 例如 `"mock_energy"` | 既有，**语义不动** |

**取值域的两个名字**（本轮定名）：

- `"simulated"` = **模拟示例**：数值由系统按定义与固定上下文生成（规格 Solution A）。
- `"user_json"` = **用户 JSON**：数值来自用户粘贴并经服务端校验的记录数组。

界面上的中文标签是「模拟示例」与「用户 JSON」；代码里一律用上面两个英文取值。

**按来源模式分叉的文案口径（v1.10.0 补登，#66 修复轮）**：界面上**每一句**说明
「这批数字是什么」的话，都必须跟来源模式**一致** —— **宁可少说，不许说假话**。

| 位置 | `"simulated"` | `"user_json"` |
| --- | --- | --- |
| 模板区域的 `pendingReason` | 「本区域数值为**模拟业务数据**，接入真实数据后自动替换。」 | 「本区域数值来自**用户提供的数据，未经业务核验**。」 |
| 用户可见回复里的来源说明 | 说「模拟业务数据」 | 说「**用户提供的数据，未经业务核验**」 |

- **模拟模式那一句逐字不许变**（既有业务输出）。
- `"user_json"` 模式下**不许**出现「模拟业务数据」，更不许宣称已连接真实业务库。
- 区域 `pendingReason` 与用户可见回复**两端口径必须一致**。
- 来源模式**从服务端记录来**（定义里记录的 / 会话提交过的 JSON 输入记录），
  **不靠标题、板块名或提示词猜**（`build_template_design` 的既有原则）。
- ⚠️ `TemplateRegion.dataSourceLabel`（既有常量「模拟数据（能耗 Mock 源，非生产事实表）」）
  在 `"user_json"` 模式下**也不准确**，但契约 §1.1 明写它「**语义不动**」，
  且前端**不渲染**它 → **本轮不改**，登记为已知限制。

### 1.2 与真实数据绑定的分界

规格第 2 条：来源模式与既有真实绑定是**并列的两个维度**，不互相覆盖。本表的分界：

| 维度 | 模拟侧（模拟字段描述，§3） | 真实侧（真实数据绑定） |
| --- | --- | --- |
| 指标身份 | `previewSpec.metrics[].metricKey` | `metricRef` / `templateBinding.metricRefs` / `dependencies.metricRefs` |
| 列身份 | `previewSpec.columns[].id` | —— |
| 取值键 | `previewSpec.columns[].fieldRef`（行对象取值键，`section_N.col_N`） | `effectiveCombination.fieldMapping[].inputFieldKey`（输入字段键） |
| 数据源 | 无（模拟不伪造数据源标识） | `sourceRef` |

**硬约束**：`sourceMode` **不改写** `metricRef` / `fieldRef` / `sourceRef` 的语义。
`sourceMode == "user_json"` 时，目录外指标**不得**被伪造成有 `metricRef`；
`sourceMode == "simulated"` 时，`sourceRef` 仍为空（模拟不伪造真实数据源标识）。

`payload.dataSource` 与 `sourceMode` **不是一回事**：前者说「这份载荷由模拟造数器产出」，
后者说「这份报表的来源模式」。来源模式**只认 `sourceMode`**。

### 1.3 六要素

| 六要素 | 内容 |
| --- | --- |
| **字段位置与类型** | **四处**同名：定义级 `metadata.sourceMode`（权威）；区域级 `region.templateBinding.sourceMode`（**可空**，覆盖定义级）；区域级预览描述 `region.templateBinding.previewSpec.sourceMode`；载荷级 `regions[].payload.sourceMode`。**取值域一致**（`"simulated" \| "user_json"`）；**可空性只有区域级那一处**（`str \| None`，`None` = 继承定义级），其余三处是 `str`。（v1.12.0 修正：原写「三处同名同类型」，漏了 `previewSpec.sourceMode`，且与自己表里区域级可空的写法打架。） |
| **候选与生效语义** | 来源模式不是「候选 / 生效」二选一，而是**生效组合里的一个维度**。待确认候选可以带自己的 `sourceMode`，但**绝不覆盖**生效组合里的来源模式；只有接受动作把它随整组绑定一起原子切过去 |
| **是否持久化** | **是**。随定义落库（`report_design_definitions.definition_json` 的 `metadata.sourceMode`），并进会话快照 `snapshot.definition`。**不**另开一列 |
| **旧数据的默认行为** | 老定义 / 老会话没有 `sourceMode` → **按 `"simulated"` 处理**。理由：ADR 0004 §5.1 已定「模板态一律用模拟业务数据渲染」，这是既有语义，不是新默认值 |
| **生产者与消费者** | 生产者：服务端（方案确认、编辑接受、JSON 输入接入时写入；**不由模型给**）。消费者：校验层（按来源分支校验）、造数器 / 装配层、渲染载荷装配、模型上下文、会话恢复、前端角标 |
| **版本校验方式** | `sourceMode` 属于 §2 生效组合的一部分，随定义版本一起比。生效组合不一致 → 候选过期、拒绝原子切换 |

### 1.4 派生行为

- 模拟模式**不受真实指标目录缺项阻断**（规格第 3 条）：准入判据是「模拟字段描述是否合法」，不是「指标目录里有没有」。
- 同一份报表**不混两种来源的数字**（规格第 51 条）：一份定义只有一个 `sourceMode`；区域级 `templateBinding.sourceMode` 不得与定义级不同（不同即校验失败）。
- `sourceMode == "user_json"` 时，**渲染载荷不落盘**；恢复时用「已保存的原始输入 + 已确认的字段映射与处理规则」重建（规格第 28 条），不重新随机选图。

## 2. 生效组合（effectiveCombination）

### 2.1 字段

落点（**本轮新增**）：`ReportDefinitionDraft.metadata.effectiveCombination`，一个对象。

| 键 | 类型 | 说明 | 现状 |
| --- | --- | --- | --- |
| `planId` | `str` | 文字方案身份 | 既有来源，组合里本轮新增 |
| `planRevision` | `int` | 文字方案版本 | 既有来源，组合里本轮新增 |
| `definitionId` | `str` | 报表定义身份 | 既有来源，组合里本轮新增 |
| `definitionVersion` | `int` | 报表定义版本 | 既有来源，组合里本轮新增 |
| `sourceMode` | `str` | 来源模式（§1） | 本轮新增 |
| `inputId` | `str \| None` | JSON 输入记录 ID；模拟模式为 `None` | 本轮新增 |
| `inputVersion` | `int \| None` | JSON 输入版本；模拟模式为 `None` | 本轮新增 |
| `fieldMapping` | `list[dict]` | 板块 / 列 → 输入字段键的映射（§2.2） | 本轮新增 |
| `processingRules` | `list[dict]` | 受控处理规则（§2.2） | 本轮新增 |

**字段映射条目**（本轮定名）：

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `regionId` | `str` | 板块（区域）ID |
| `columnId` | `str` | 列 ID |
| `inputFieldKey` | `str` | 输入 JSON 里的字段键 |
| `inputFieldPath` | `str \| None` | 嵌套路径；扁平结构时为 `None` |

**处理规则条目**（本轮定名）：

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `ruleId` | `str` | 规则稳定 ID |
| `operation` | `str` | 受控操作枚举，见下 |
| `targetFieldKey` | `str` | 作用的目标字段键 |
| `params` | `dict` | 操作参数；**只允许标量与受控枚举**，不执行表达式 |

受控操作枚举（**本轮定名，取值域固定**）：`PASSTHROUGH`（默认直接展示）、`SUM`、`AVG`、
`COUNT`、`GROUP_BY`、`RATIO`。

> 扩展这个枚举要升契约表次版本。

**生效组合的同级字段（v1.5.0 补登，#64）**：`ReportDefinitionDraft.metadata.jsonInputIssues`
——`{unmappedColumns: [...], dataIssues: [...]}`。**纯结构与说明文字，不含业务数值**。
放在 `metadata` 下与 `effectiveCombination` **平级**，**不进**生效组合本身（组合的 9 键固定不变）。
它记的是「哪些列没绑上」「数据里有哪些问题」，供界面把话说清楚。

**执行侧的硬边界（v1.5.0 补登，#64）**：
- 处理规则的 `operation` **只允许受控枚举**；`EXEC` / `expression` / `sql` 一律拒绝。
- `params` **只允许标量与受控枚举**，**不执行**模型或 JSON 生成的代码、SQL 与任意表达式。
- 温度、PUE、累计电表读数、编号**不默认求和**；求和 / 平均 / 分组 / 派生计算须有业务依据、
  在方案或修改计划里说明、**让用户确认**。
- `null`、**缺失**与 `0` **区分开**；没有日期不编趋势；无效日期或混合类型**降级明细展示或明确指出数据问题**，不强制编值**也不丢行**。

### 2.2 六要素

| 六要素 | 内容 |
| --- | --- |
| **字段位置与类型** | `ReportDefinitionDraft.metadata.effectiveCombination`（dict）。它与 `metadata.templateBinding.definitionId` / `.definitionVersion` **必须一致**——后者是既有的预览上下文锚点，值由同一处一次成型，不另存第二份真值 |
| **候选与生效语义** | **待确认候选与生效组合分开保存**（规格第 30 条）。候选可以保存用于继续设计，但**绝不覆盖**已确认的输入、来源与字段映射。右侧面板继续显示当前生效的组合 |
| **是否持久化** | **是**。随定义落库（`report_design_definitions.definition_json`），并进会话快照 `snapshot.definition`。候选侧只保存**待确认候选**本身（不写生效组合） |
| **旧数据的默认行为** | 老定义没有 `effectiveCombination` → **按空组合处理**：`sourceMode = "simulated"`、`inputId = None`、`inputVersion = None`、`fieldMapping = []`、`processingRules = []`；`planId` / `definitionId` / 版本号从既有 `metadata.templateBinding` 回填。老会话**不伪造**已生效报表（规格第 33 条） |
| **生产者与消费者** | 生产者：服务端确认路径（确认方案 / 接受修改 / JSON 输入接入）**原子**写入。消费者：编辑、渲染、校验、运行、会话恢复、模型上下文（规格第 44 条要求这些消费者读同一份生效版本） |
| **版本校验方式** | 提交前做**版本比较**再**原子提交**（规格第 32 条）：模型工作与载荷生成在事务外，校验通过后比版本、一次提交。取消、解析 / 校验失败、造数失败、版本冲突**一律保持旧生效组合** |

### 2.3 边界

- 「既有确认边界保留」（规格第 34 条）：新建文字方案的确认与模板编辑计划的接受是**两种独立确认**，不合成同一状态。
- 示意生成**不等于**真实业务核验成功，不得提前标成「已校验」。
- 本轮**不**引入真实取数通道；`sourceMode == "user_json"` 的数据来自用户粘贴，不是业务库。

**描述的来源链（v1.7.0 补登，#59 修复轮）**：`previewSpec.columns[]` 的语义描述由
**转换层**写，转换层的输入是**方案层的定稿列**：

| 环节 | 落点 | 说明 |
| --- | --- | --- |
| 模型声明 | `ReportPlan.columns[]`（`schemas/report_plan.py` 的 `PlanColumn`） | **本轮新增** `semanticKind` / `valueType` 两个**可选**字段。模型写错枚举值**不当场作废方案**（域外当没声明） |
| 定稿 | `report_plan_service.finalize_columns()` | 模型这次声明了就用这次的；没声明就**沿用上一版**的（列的身份没换，语义就不该自己变） |
| 转换 | `template_definition_service._build_preview_spec()` | 把定稿列的声明写进 `previewSpec.columns[]`；模型没声明的那部分**由 §3.4 的链解析** |

> ⚠️ **① `declared` 在生产路径上目前不可达**（v1.18.0 订正，#59 B1 独立复核实测）：
> 方案层定稿列**确实带上了**这两个字段（`PlanColumn.semanticKind` / `valueType` 实测有值），
> 但**模板层** `report_template_service._normalize_columns` 只透传 `id` / `label` / `fieldRef` / `format`
> —— `TemplateColumn` 是**封闭 schema**（`extra="forbid"`，`schemas/template_design.py`），
> **这两个字段在这一层被丢弃** → 到转换层时列上已经没有声明了。
> 实测（完整生产链）：模型给 `{"label": "神秘列", "valueType": "energy", "semanticKind": "energy"}`
> → 载荷里该列 `valueType=text`、值是**占位文本**，走的是 ⑤ 不是 ①。
> **为什么本轮不接**：接通它（模板层开放这两个可选字段并透传）会让**模型声明的语义优先于兜底链**
> → **改既有业务输出**（现有方案里模型声明与兜底链不一致的那些列，数值会变）。
> 本轮**不做**，登记为已知限制，**另开一票**做这个行为变更。
> **B1 不依赖 ①** —— 模型不声明照样能出数（走 ② / ③ / ④）。

> 模型**没有**义务声明这两个字段 —— 声明了走 ① `declared`，没声明照样能出描述，
> 走 ② / ③ / ④。**模型不声明不是错误。**

### 3.2 语义类别与值形态

**语义类别**（`kind` / `semanticKind`，取值域固定）：`energy`、`cost`、`pue`、`power`、
`alarms`、`cabinet_status`、`generic`。

`generic` 的含义是「认得出来它是模拟示例，但认不出业务口径」——**明确标注为模拟的示例**，
不是留空。

**值形态**（`columns[].valueType`，本轮定名，取值域固定）：`level`、`status`、`time`、
`device_id`、`device_type`、`device_name`、`pue`、`power`、`cost`、`energy`、`percent`、
`count`、`duration`、`temperature`、`voltage`、`current`、`description`、`text`。

> 这套取值域**照抄现有 `simulated_data_service._column_value_kind` 的判定结果集**
> （`backend/app/services/simulated_data_service.py`），只是把「按列名猜」换成
> 「按描述读」。既有函数本轮删除（规格第 5 条：那是 ADR 0004 §5.4 的现存违反点）。

### 3.3 确定性上下文

**确定性上下文的权威落点是既有的 `previewContext`**（会话快照 `snapshot.previewContext`
与载荷 `previewContext`），字段不变：`definitionId` / `definitionVersion` / `timezone` /
`anchorTime` / `windowStart` / `windowEnd` / `grainUnit` / `generatorVersion`。

模拟字段描述里**不重复存时间窗**，只声明**该字段的数值依赖哪一层作用域**：

```text
deterministicScope = {
  "scope": "region" | "metric_family",   # 区域级噪声 / 量族级（如同比）
  "seedKey": str                          # 种子材料标识（区域标识或量族标识）
}
```

既有规则照旧：同一份定义、同一时间窗 → 数字恒定；跨板块同口径同窗口共用基础样本；
同比按**量族**给，不按区域给。

**`deterministicScope` 的效力边界（v1.6.0 补登，#59 验收 M1 后提出）**：
`deterministicScope` 是**预期作用域的记录**，**当前不由它决定造数种子**。
造数种子仍由造数器既有逻辑按区域 / 量族生成——**改种子就是改既有业务输出，本轮不动**。
因此：

- **不变量不变**（上一段那三条照旧成立）：同一份定义、同一时间窗 → 数字恒定；
  跨板块同口径同窗口共用基础样本；同比按量族给。
- **它现在的作用**：随定义版本一起走，供模型上下文与校验层读取，说明「这个字段的数值
  预期依赖哪一层作用域」。
- **它不作为什么**：不得被当作「种子已由它决定」来断言，也不得据此推断两份定义
  的数值一定相同。

### 3.4 六要素

| 六要素 | 内容 |
| --- | --- |
| **字段位置与类型** | `region.templateBinding.previewSpec`（既有结构，本轮扩字段）。指标类字段的身份 / 取值键 = `metrics[].metricKey`；列类字段的身份 = `columns[].id`、取值键 = `columns[].fieldRef` |
| **候选与生效语义** | 字段描述**跟着定义版本走**：候选定义里的字段描述**不生效**，直到被接受并原子切到新的生效组合。生效组合里的字段描述是造数器唯一的输入 |
| **是否持久化** | **是**（纯结构：语义类别、单位、身份、取值键、能力标记）。**不含任何样例业务数值**——模拟业务数值仍然只在响应与内存（ADR 0004 §5.1） |
| **旧数据的默认行为** | 老定义没有 `previewSpec` → 造数器退回既有执行绑定的指标引用；认不出来就是 `generic`（明确标注为模拟的示例），**不因此留空**。老定义没有 `columns[].semanticKind` / `valueType` → 按**确定性回退链**解析（v1.4.0 裁定，与 #59 实现一致，见下表） |
| **生产者与消费者** | 生产者：转换层（`template_definition_service`）与编辑引擎写入定义；**不由模型直接给**。消费者：造数器（`simulated_data_service`）、示意载荷装配、校验层、前端单位 / 指标读取 |
| **版本校验方式** | 字段描述随定义版本走（`definitionId` + `definitionVersion`）。旧版迟到结果不得覆盖新版（规格第 13 条）：造数前比对版本，不一致即丢弃 |

**老定义兜底链（v1.4.0 裁定）**：老定义没写描述时，按下面这条链**逐级**判定，只用**声明过的事实**：

| 级 | 来源 | 判定依据 | 命中后 |
| --- | --- | --- | --- |
| ① `declared` | 列**显式声明** | `columns[].valueType` / `columns[].semanticKind` | 直接采用 |
| ② `unit` | 列**声明的单位** | `columns[].format.unitLabel`（方案侧的定稿列**没有独立的 `unit` 字段** —— `PlanColumn` 是封闭 schema（`extra="forbid"`），单位只走 `format.unitLabel`），单位对照单位 → 值形态表 | 取该单位对应的值形态 |
| ③ `identity` | 列的**字段身份** | `columns[].id` / `columns[].fieldRef` 及其末段，命中规范字段目录里**能唯一确定量口径**的具体条目（如 `energyKwh` / `costYuan` / `powerKw` / `deviceName`）。**通用量词不算**（v1.18.0 收紧）—— `energy` / `cost` / `power` / `kwh` / `kw` / `yuan` 这类只说明「是个量」，不说明「是哪个量」 | 取该条目的值形态与单位 |
| ④ `vocabulary` | 列的**显示名** | 显示名**先剥掉已知的单位括号标注**（如 `前一日耗电 (kWh)` → `前一日耗电`），再**精确命中**产品栏目封闭词表（不是模糊匹配、不是关键词猜测）（v1.18.0 补登「剥单位标注」这一步） | 取该条目的值形态与单位 |
| ⑤ `unresolved` | —— | 以上都不成立 | `semanticKind = generic`、`valueType = text`（**明确标注为模拟的示例**，不猜） |

**这条链与「按列名猜」不是一回事**，§8 不变量 5 依然成立：

- 被删掉的是 `simulated_data_service._column_value_kind` 那种**按列名模糊猜**（ADR 0004 §5.4 的现存违反点），本轮确实删除；
- ③ 用的是**字段身份**（列的 id / 取值键），不是标题；④ 用的是**封闭词表的精确查表**，命中不了就是命中不了；
- 兜底链**不是**只服务历史数据 —— 它是**通用的解析路径**，**生产路径也走它**
  （`template_definition_service._build_preview_spec` → `simulated_field_semantics.describe_simulated_field`）。
  ① `declared` 只是「模型这次声明了」这一档；新定义没声明时同样从 ② 起跳，
  老定义因为根本没有这两个字段才**必然**从 ② 起跳。**两者是同一条链、同一份代码。**
  （v1.7.0 修正：原表写「兜底链只服务历史数据……新定义不走兜底」，与实现对不上。）

### 3.5 与真实绑定的分界

- 目录内指标：`bindingKind = "catalog"`，`metricRef` 指向真实指标目录，`simulatedId = None`。
- 目录外指标（如「电脑耗电量」）：`bindingKind = "simulated"`，`metricRef` 为空，
  `simulatedId` 是服务端生成的**稳定模拟身份**（不伪造成真实 `metricRef`，规格第 19 条）。
- 目录外指标**不静默映射**到「总耗电」这类已有指标（规格第 6 条）；语义不明时先澄清或标为显式假设。
- **别名命中 ≠ 识别成功**（v1.8.0 补登，#65 验收 AC1 缺口后）：
  指标目录的别名表是**子串匹配**（`metric_mock_service.match_metric_by_alias`），
  于是「设备耗电**率**」因为**包含**别名「设备耗电」会被判成已登记指标。
  **判据是「量口径变没变」，不是「字符串差了几个字」**：
  - 用户/模型说的口径**本身**不是已登记指标名（只是**包含**某个别名）
    → **按目录外处理**（`bindingKind = "simulated"`、`metricRef` 为空），
    出**可澄清**的问句或**带显式假设**的候选。
  - 说的就是那个别名、或只是加了**同义后缀**（「设备耗电」「总耗电量」）
    → 仍然命中已登记指标，**既有行为一个字都不许变**。
  - 只加**展示要求**的口径（「设备耗电排名」）→ 量口径没变，**仍然命中**。
  - **判定谓词只有一份**，放在共享语义层（`simulated_field_semantics`），
    **编辑侧与方案侧用同一套** —— 两处各写一份必然漂移。
    **落点**：`simulated_field_semantics.intent_names_registered_metric()`
    （#65 修复轮把编辑引擎里的模块私有副本搬进共享层，编辑侧改成 import）。
  - **别名表本身不改**（`context_engine` / `routing_rules` / `report_template_service` 都在用），
    改**消费方**。
- JSON 模式下，列到输入字段的真实绑定在 `effectiveCombination.fieldMapping`，**独立于**
  `columns[].fieldRef` 这个模拟取值键（规格第 23 条）。

## 4. 四类版本标识

四类对象各有各的版本，**互不替代**。比较规则全部是「期望值 vs 当前值」严格相等。

> 另有一类**规则库版本**（§4.1.1）——它记的是「这份方案当时按哪一版规则定稿的」，
> 不是对象版本，不参与上面四类的过期判据。

### 4.1 文字方案（plan）

| `planId` / `planRevision` | `TemplateDesign` | `str` / `int` | 模板绑定的方案身份与版本 | 既有 |
| `planId` / `planRevision` | `report_design_templates` 表列 | `str` / `int` | 同上，模板表冗余存一份 | 既有 |

| **生产者与消费者** | 生产者：领域服务 `report_plan_service.apply_candidate`（新建从 1 起；修改**沿用**上一版 `id`，`revision` 递增）。消费者：设计存储的提交 / 冲突判定、确认关系、模板绑定、前端卡片 |

| `schema_json` | 同表 | `str` | 字段结构、缺失与类型统计 | **本轮新增** |
| `sample_json` | 同表 | `str` | 有上限的代表样本 | **本轮新增** |

| `byte_size` | 同表 | `int` | 字节数 | **本轮新增** |

服务层用 `inputId` / `inputVersion` 两个名字（表列是蛇形，Python / JSON 是驼峰）。

规模上限（规格第 20 条，本轮定死）：**1 MB / 5,000 行 / 50 个字段**，
任一超限**明确拒绝并提示**，不截取通过。

**代表样本上限（v1.5.0 补登，#64）**：模型上下文里的样本**最多 5 行**。
样本**只**给模型看，**最终渲染与处理用完整已校验数据** —— 样本不得被当成报表数据。

**数组位置标记（v1.5.0 补登，#64）**：报文里**多个数组**时服务端**不替用户挑**（规格第 31 条）。
用户用下面任一写法指定：

```
数组位置: data.records
@arrayPath data.records
```

写不出 / 写错 / 有歧义 → 明确报错，不猜。

> ⚠️ **标记必须独立成行**（v1.11.0 补登，#66 独立核验后登记）：
> 写在**同一行**（如 `这是数据 {"data":{"r":[…]}} 数组位置: data.r`）会被
> **静默忽略** —— 服务端按「唯一数组」自动挑了那个数组，**不作任何提示**。
> 按契约的写法（独立成块）是对的；这里登记的是**已知限制**，
> 免得用户以为「我写了位置但系统没理我」。
> 改成给一句提示 = 变更既有行为，**本轮不做**，需要时另开一票。

**校验失败码（v1.5.0 补登，#64）**：响应 `error.code` 取值固定，不合并：

`JSON_INPUT_EMPTY` / `JSON_SYNTAX_INVALID` / `JSON_NOT_ARRAY` / `JSON_ARRAY_EMPTY` /
`JSON_ARRAY_PATH_INVALID` / `JSON_ARRAY_PATH_AMBIGUOUS` / `JSON_NESTED_NOT_SUPPORTED` /
`JSON_ROW_NOT_OBJECT` / `JSON_TOO_LARGE` / `JSON_TOO_MANY_ROWS` / `JSON_TOO_MANY_FIELDS`

文案要写成「哪里不对、怎么改」，可直接展示给用户。

**JSON 模式的载荷补充字段（v1.5.0 补登，#64）**：

| 字段 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `notes` | `regions[].payload.notes` | `list[str]` | **区域自己的**口径说明（纯文字，不含业务数值）；**不放全局数据问题**（§4.3.2 ⑤） |
| `recordCount` | `regions[].payload.recordCount` | `int` | 记录总行数 |
| `displayedRows` | `regions[].payload.displayedRows` | `int` | 本区域实际显示的行数（明细表**最多 200 行**，汇总计算用全部行） |

**截断判据（v1.19.0 补登）**：`recordCount > displayedRows` 即为**截断** —— 前端据此出截断提示。
**JSON 模式与模拟模式同一条判据**（早期版本只有模拟模式出提示，是漏的一处，#66 修复轮补上）。

**JSON 模式的指标卡**：`yoyPercent = null`、`comparisonAvailable = false` —— 用户数据没有同比口径，**不编**。

**JSON 模式的单位**：只认方案声明的 `format.unitLabel`，没有就是 `""` —— **不猜 kWh**。

**JSON 模式的来源标记（v1.15.0 补登，#66）**：`AgentResponse.debug.jsonInput`
（**既有键**，#64 引入）= `{accepted: bool, inputId, inputVersion, recordCount, fieldCount, byteSize}`
（校验失败时 `accepted=false` 且带 `code`）。
**只有引用，没有原始数组**（§4.3「普通聊天消息只存安全摘要与引用」）。
**出方案的那一轮（设计流程那一轮）也带这个键**，形状与非设计轮**完全一致** ——
前端在收到方案那一轮就能判断「这是用户 JSON 模式」。
不是 JSON 输入的轮次，响应里**不多出**这个键。
**不新增顶层响应字段，不改 `AGENT_PROTOCOL_VERSION`。**

**绑定失败的表现（v1.5.0 补登，#64）**：字段映射绑不上时，该列显示「（未绑定）」并降级明细展示，**不编值**。

| 六要素 | 内容 |
| --- | --- |
| **字段位置与类型** | 独立表 `report_design_json_inputs`（本轮新增）。身份 `inputId`（`str`）+ 版本 `inputVersion`（`int ≥ 1`） |
| **候选与生效语义** | 新粘贴 / 更新产生**新版本**（`inputVersion` + 1）；**旧版本不删除**（老数据不迁移、不删除）。生效组合只认已确认的那一版（`effectiveCombination.inputId` + `.inputVersion`）。**候选不覆盖生效输入** |
| **是否持久化** | **是，且只存这一份原始数据**（规格第 21 条）。普通聊天消息只存安全摘要与引用，不复制完整数组；诊断记录与调试跟踪**也不复制** |
| **旧数据的默认行为** | 老会话**没有历史输入** → 明确提示「当前没有历史输入」，**不从模拟数字冒充恢复实际数据**（规格第 29 条）。老会话的 `sourceMode` 按 `"simulated"`（§1.3） |

#### 4.3.1 JSON 模式的载荷口径：指标值、规则说明、图表轴与单位（v1.14.0 补登）

code-review R2（后端数据层）在 JSON 载荷层查出三处「**说的和做的不一样**」。
统筹裁定如下 —— 这三条是**硬口径**：界面上每一句关于「这批数字是什么」的说明，
都必须与实际执行的处理一致（对应 §8 不变量 8）。

**① 指标卡的值只能来自实际生效的处理结果 —— 不许拿第一行冒充**

| 情形 | 指标卡的值 | 说明（`notes`）要写什么 |
| --- | --- | --- |
| 方案为该指标声明了受控汇总规则（求和 / 平均），且该规则**实际执行了** | **规则的实际结果** | 写明按什么口径汇总 |
| 汇总规则是**分组 / 占比**（结果是一组值 / 一行一个比例） | **留空**（`null`）—— **没有单一合计**，不许取第一组 / 第一行 | 写明「这不是一个单独的数值，分项数值请看明细表或图表」 |
| 汇总规则**被跳过**（温度 / PUE / 累计电表读数 / 编号不默认求和） | 按下面两行走 | 写**实际发生了什么**（复用「不默认求和」的人话口径），**不许**写「按求和展示（……用户已确认）」 |
| 规则执行了，但**这一列没有可求和的数值**（求和 / 平均遇到一列文字） | **留空**（`null`）—— 是「没有数」，**不是 0** | 写「方案声明了求和口径，但这一列没有可求和的数值，没有编合计值；要逐行看数值请看明细表」。**不许**显示字符串 `"null"` |
| 没有声明汇总规则，输入**只有 1 行** | 该行的输入值 | 写明是按输入值直接展示 |
| 没有声明汇总规则，输入**有多行** | **留空（不编合计值）** | 写明「方案没有为这个指标声明汇总口径、共 N 行、没有编合计值，要逐行看数值请看明细表」 |

多行且无口径时按规格第 25 条「依据不清时用明细表」处理 ——
把第一行的值放进一个写着「总耗电」的指标卡，是**说假话**。
载荷形状不变（仍是指标卡载荷，`metrics` 结构照旧），前端不需要跟着改。

**② 规则被跳过时，说明必须写实际发生了什么**

方案声明了求和、但该字段属于「不默认求和」（温度 / PUE / 累计电表读数 / 编号）时，
这条求和**不执行**。此时口径说明**必须**写「求和没有业务意义，已按明细展示」这类实话，
**不许**写「按求和展示（……用户已确认）」—— 那是把没做的事说成做了。

**③ 「累计电表读数不默认求和」（规格第 25 条）的词表要覆盖 meter 族写法**

判定按**词段精确匹配**（不是裸子串：裸子串会把 `grid` 含 `id` 误判成编号类字段）。
`meter` / `电表` / `meterTotal` / `total_meter` / `meter_total` / `electricity_meter` /
`电表累计` 等写法都要命中「不默认求和」；命中就**不生成求和 / 平均规则**，
改用明细展示并写明原因。

**④ 图表的轴只能按方案声明选 —— 不按列名猜（ADR 0004 §5.4）**

选取顺序固定（**逐轴**判断 —— 只声明了 X 轴时，Y 轴走 ②，反之亦然）：
① 区域 `component.encodings` 的 X / Y 通道 → `fieldRef` → 字段映射；
② **那条轴** encodings 没声明时，用**区域声明的列**里 `valueType` 为 `time` 的那一列作横轴、
`valueType` 为数值类的那一列作纵轴。
**只声明了 `semanticKind` 时，按语义类别推导值形态**（契约 §3.4 的 ① 级）；
**两者都不声明就是不声明 —— 不猜**。
> ⚠️ `semanticKind` 的取值域（§3.2）里**没有**时间 / 日期类 ——
> 时间 / 日期类在**值形态**（`valueType = "time"`）上，不在语义类别上。
> （v1.17.0 订正：原文写成「`semanticKind` 为时间 / 日期类」，在 schema 上不可满足。）

**禁止**「列 id 含不含 `date` / `time`」「挑任意另一列」这类按名字 / 按位置猜的取法。
取不到轴 → 空点 + 说明「已降级明细展示，没有编趋势」（沿用该模块既有降级口径）。

**⑤ 图表的单位只认方案声明**

图表 `unit` 取 **Y 轴那一列**声明的 `format.unitLabel`，与指标卡**同一套取法**
（同一个取单位的函数，不许两处各写一套）；方案没声明单位就是空串，**不猜 kWh**（规格第 24 条）。

**⑥ 口径说明的措辞只有一处出处（v1.16.0 补登；v1.17.0 补一条）**

指标卡与图表的口径说明文案写在 `json_payload_service` 里，**下游票不要另写一套说法**。
文案只写「口径与数据问题」，**不含业务数值**。

**措辞要按实际规则说（v1.17.0 补登）**：`GROUP_BY` →「分组的结果是每组一个值」；
`RATIO` →「占比的结果是每行一个比例」；`SUM` / `AVG` →「这条汇总口径算不出一个单独的数值」。
**不许**把求和 / 平均说成「占比」。
**「按求和展示（……用户已确认）」只在真的求出了数的时候才出现** ——
没求出来就不写「用户已确认」（那是把没做的事说成做了）。

**指标卡的 `value` 允许为 `null`**：未绑定 / 无记录 / 无单一合计时都是 `null`，
前端渲染成「—」。**「没有值」不许被当成 0** 参与任何合计（那是在把「不知道」说成「零」）。

### 4.3.2 前端怎么消费 JSON 载荷里的说明文字（v1.19.0 补登，#66 修复轮）

code-review R3（前端路）查出：服务端写在载荷里的**实话**（截断提示、字段缺失、规则被跳过……）
前端**一个字都没渲染**，用户看不到。修复轮把这些端到屏上，同时暴露出「同一句话说多遍」的新问题。
本节把**前端消费这些说明的口径**定死 —— 载荷的**形状不变**（承 §4.3.1 的约定）。

**① `regions[].payload.notes` 的类型是 `list[str]`**

逐条渲染，每条一行。服务端给什么顺序就什么顺序，**前端不重排、不合并、不总结**。

**② 截断判据是 `recordCount > displayedRows`**

前端据此出截断提示（例：「共 N 行，已显示前 M 行」）。
**JSON 模式与模拟模式同一条判据** —— 早期版本只有模拟模式出提示，是漏的一处。

**③ `metadata.jsonInputIssues` 的渲染位置与格式**

渲染在**报表面板顶部**（区域卡片之前），一个区块、两段：

- 「以下栏目没能绑定到输入字段：」—— 逐列：`「列名」（所属区域）——原因`
- 「数据里的问题：」—— 逐条原文

**④ 前端逐字渲染，不改写、不总结**

服务端写好的是**事实**。前端**不许**改写措辞、不许概括、不许自己补判断，
也不许把「没有值」当成 0 参与任何合计（承 §8 不变量 8「宁可少说，不许说假话」）。

**⑤ 全局数据问题只说一次（v1.19.0 裁定）**

`metadata.jsonInputIssues.dataIssues` 记的是**整份报表**的数据问题（不是某一个区域的），
所以它**只在面板顶部出现一次**；**不许**再塞进每个区域的 `payload.notes` ——
否则同一句话在界面上会出现「顶部 1 次 + 每个区域各 1 次」（N+1 遍）。

区域 `payload.notes` **只放区域自己的话**：截断提示、本区域某列没绑上、
本区域的指标没有值、规则在**这个区域**被跳过、趋势降级说明等。

> 这条是对实现的**裁定**：R3 修复轮之前，服务端把 `dataIssues` 整份塞进了每个区域的 `notes`
> （`simulated_data_service` → `json_payload_service`），前端又在顶部渲染了一遍 → 用户看到一堆重复的黄条。
> 修复方向：**服务端不再把全局问题塞进区域 `notes`**（区域专属的话**一条不少、一字不改**）。

## 5. 有效菜单与输入锁（effective menu / input lock）

### 5.1 字段

| 字段 | 位置 | 类型 | 取值 | 现状 |
| --- | --- | --- | --- | --- |
| `pending_choice` | `sessions.pending_choice` 列 | `str`（JSON） | `{state, question}` | 既有 |
| `question.selectionOnly` | `pending_choice.question.selectionOnly` | `bool` | `true` = 只允许从选项里选 | 既有 |
| `question.options` | `pending_choice.question.options` | `list[{value,label}]` | 非空 = 有可选项 | 既有 |
| `question.id` | `pending_choice.question.id` | `str` | 菜单身份（`template_edit_confirm` / `pending_edit_plan_confirm` / …） | 既有 |
| `question.lockScope` | `pending_choice.question.lockScope` | `str` | `"none"` \| `"menu_only"` \| `"input_and_menu"` | **本轮新增** |
| `lockedChoice` | 前端 `workbench.js` 进程内变量 | `object \| null` | 当前有效菜单对象 | 既有 |

**`lockScope` 取值语义**（本轮定名）：

| 取值 | 锁什么 | 用在哪个阶段 |
| --- | --- | --- |
| `"none"` | 不锁 | 历史菜单失效后；已选「继续调整」进入统一对话 |
| `"menu_only"` | 下拉框 + 快捷入口；**输入框与发送按钮保持可用** | 既有行为的默认值（编辑态、确认态） |
| `"input_and_menu"` | **输入框 + 发送按钮 + Enter 键** + 下拉框 + 快捷入口 | 「右侧模板已生成、等待下一步操作选择」这一阶段 |

### 5.2 判定规则

**有效菜单**（前后端同一个判据）：

```
pending_choice 非空
AND pending_choice.question.selectionOnly == true
AND pending_choice.question.options 非空
→ 当前存在一份有效菜单
```

**输入锁**：

```
lockScope == "input_and_menu" → 锁输入框、发送按钮、Enter、快捷入口、下拉框
lockScope == "menu_only"       → 只锁快捷入口与下拉框；输入框与发送按钮可用
lockScope == "none"            → 什么都不锁
lockScope 缺失                 → 按 "menu_only" 处理（老数据默认行为，见 §5.3）
```

> **v1.4.0 修正**（#62 实施时提出）：原表此处写「`none` / 缺失 → 不锁」，与 §5.3「老会话的 `pending_choice.question` 没有 `lockScope` → 按 `"menu_only"` 处理」自相矛盾。**以 §5.3 为准**：缺失按 `menu_only`。
> 两者对「输入框能不能打字」的影响相同（都不锁输入），差别只在下拉框与快捷入口——老会话按今天的既有行为走，即 `menu_only`。代码已按此实现。

**阶段判据**：服务端**当前状态**与**有效菜单**共同决定，不由历史消息推断
（规格第 54、57 条）。具体地：

- 「文字方案阶段」——该阶段**没有** `selectionOnly` 菜单（确认方案是方案卡片上的按钮，
  不是菜单），所以 `pending_choice` 为空 → 天然不锁。
- 「模板已生成、等待下一步操作选择」——菜单 `question.id == "template_edit_confirm"`
  且 `prompt == "请选择下一步操作："`，本轮在生成这份菜单时写 `lockScope = "input_and_menu"`。
- 「待接受修改计划产生时恢复选择锁」——菜单 `question.id == "pending_edit_plan_confirm"`，
  `lockScope = "input_and_menu"`；用户选「继续调整」后该菜单失效 → `lockScope = "none"`。

**刷新后按服务端恢复**：前端 `restoreSession` 从 `detail.pendingChoice.question` 恢复锁
（既有路径），本轮改为读 `question.lockScope` 决定锁到哪一层，**不再只靠进程内状态**。

### 5.3 六要素

| 六要素 | 内容 |
| --- | --- |
| **字段位置与类型** | 权威落点：`sessions.pending_choice`（`{state, question}`，既有）。判定字段：`question.selectionOnly`（bool）+ `question.options`（非空）+ 本轮新增 `question.lockScope`（枚举）。前端消费副本：`lockedChoice`（进程内）+ `question.lockScope` |
| **候选与生效语义** | **只有一份有效菜单**：后端 `pending_choice` 指认的那份。历史消息里的菜单**一律失效**（规格第 57 条），回放不得把已答掉的菜单摆回来、更不得据此锁输入 |
| **是否持久化** | **是**：`sessions.pending_choice` 独立列（既有）。前端 `lockedChoice` 是进程内副本，**不是**权威 |
| **旧数据的默认行为** | 老会话的 `pending_choice.question` 没有 `lockScope` → **按 `"menu_only"` 处理**，等于今天的行为（不锁输入）。老会话若有 `pending_choice` → 仍认它是一份有效菜单 |
| **生产者与消费者** | 生产者：服务端生成菜单的路径（`agent_service._remember_choice`、`report_design_service` 落库处）——**同一个菜单对象既有响应又有落库副本，不允许两处各拼一份**。消费者：后端拒收自由输入（`_pending_choice_required`）、前端输入框 / 发送 / Enter / 快捷入口 / 下拉框 |
| **版本校验方式** | 菜单**没有版本号**。它的「有效性」由**服务端当前状态**决定：`pending_choice` 被清空（用户已选 / 取消 / 阶段推进）即失效。界面锁定**只是引导**（规格第 56 条）；真正的边界是后端对确认与权限的校验——直接调接口在等待选择期间仍不能绕过确认 |

### 6.2 生成与落点

- `requestId`：**服务端**在模型适配层生成，**每次模型调用一个**，不跨轮复用。
  会话标识 `conversationId` **不能**用来区分请求（它跨轮复用）。
  重试产生新的 `requestId` + 递增的 `attempt`，**不覆盖**上一次。
- 异步调用用**请求级上下文**关联（`ContextVar` 既有机制，见 `request_timeline.py`），
  不使用可被并发覆盖的全局「上一次响应」变量。
- 上游元信息在**模型客户端丢弃响应之前**采集。现有模型调用契约仍返回纯文本，
  **本轮不改变该契约**，只在适配处采集元信息。
- `diagnosticId` 在**写诊断文件时**生成，一条诊断记录一个。
- 诊断文件落点：**仅当前用户可读写的受限本机目录**（目录 `0700` / 文件 `0600`），
  **不在**前端公开目录、**不在** Git 仓库、**不进**普通 API 响应、**不进**用户可见错误消息、
  **不上传**第三方平台。

### 6.3 失败分类（三者不混）

本轮定名（`parseStatus`）：

| 取值 | 含义 |
| --- | --- |
| `"PARSE_NOT_JSON"` | 返回格式损坏（不是 JSON 对象） |
| `"PARSE_STRUCTURE_INVALID"` | 是 JSON 但结构非法 |
| `"TERMINAL_RESULT_MISSING"` | 未提交合法终结结果 |
| `"OK"` | 解析与校验都过了 |

三类在日志与诊断里长得一样正是要解决的问题（规格 Problem Statement 第 43 行），
所以**必须分开记**，不能合并成一句「模型输出无法解析」。

### 6.4 六要素

| 六要素 | 内容 |
| --- | --- |
| **字段位置与类型** | `requestId`（`str`）与元信息由模型适配层产出，随**日志行**与**诊断记录**传递。`diagnosticId`（`str`）是诊断记录的独立标识。诊断记录是**独立文件**，不落会话库 |
| **候选与生效语义** | 无候选 / 生效之分。标识**只做关联**，不做业务判定 |
| **是否持久化** | **诊断记录**：落受限本机目录的独立文件，**不落会话数据库**、**不落普通日志文件**。**常规日志**：只写标识与元信息（`requestId` / `attempt` / `stage` / `modelId` / 耗时 / 长度 / 分类），**不写**用户原话、模型返回原文、上游异常原文、凭据、原始 JSON、业务数字（规格第 66、67 条） |
| **旧数据的默认行为** | 没有旧数据可默认——本轮**新增**。既有日志里已经在泄漏原文的调用由 #61 接管；接管前那些行**不追溯处理** |
| **生产者与消费者** | 生产者：模型适配层（`requestId` + 元信息）、解析层（`parseStatus` + 位置信息）、诊断写出层（`diagnosticId`）。消费者：常规日志（排查）、诊断记录（复盘）、#61 的旧日志接管 |
| **版本校验方式** | 标识**不做大小比较**，只做等值关联。诊断记录里的 `requestId` 与日志行里的 `requestId` 相同即对上。诊断记录另记 `outputTotalLength` 与 `truncated`：**诊断截取不得被误判为模型输出截断** |

### 6.5 硬边界

- 精确原文模式**默认关闭**；本轮只实现显式、限时、限范围的开关，**不开启**、不采集现有会话原文。
- 脱敏拿不准就**不写内容**，只留元信息并写明原因（`contentOmittedReason`）。
- 写日志 / 写诊断**失败不得让业务请求失败**。
- 日志量、文件大小与轮转沿用现有配置（`logging_config.py`：`maxBytes=10MB`、`backupCount=5`、`0600`）。
- 诊断改动**不改变模型行为**：不改提示词、解析、重试，不做心跳 / 取消重构。
- **失败时留调用栈（v1.13.0 补登）**：失败日志**要带调用栈** ——
  口径与路由层一致（`exc_info=(类型, None, traceback)`）。
  **栈里只有代码位置**：异常消息、用户原话、模型返回原文、用户 JSON 原文、凭据、
  业务数值**一律不进栈也不进日志参数**。
  模型调用失败这条路**原本不留栈**（路由层一直留），导致排查的人拿不到「炸在哪一行」——
  这正是 #57 要解决的那类问题，本轮补齐。
  ⚠️ Python 的调用栈会打印**源码行** → 前提是源码里**不写死敏感串**
  （仓库既有约定已覆盖）；这条与路由层的既有行为**完全一致**，不是新的泄漏面。

### 7.3 硬边界

- 一次生成或调整意图**最多一轮**主动澄清，每轮一到两个关键问题。
- 一轮之后仍缺安全目标时：**保留当前报告**并给非阻塞说明与可选替代，**不猜目标、不造空计划**。
- 用户说「你自己决定 / 别问了」后**停止阻塞**并给可见假设，**不代用户接受**。
- 咨询与问题反馈**只追加聊天**：不改定义版本、不改待确认计划、不改业务阶段，不自动保存、校验或试运行。
- 咨询与问题分析**复用既有的只读事实查证与回答契约**（同一套四态事实语义）；查询工具与执行工具的权限**不合并**，业务对象**不重建**。
- **「复用」指同一份实现（v1.20.0 补登）**：咨询与问题反馈两条路径都由
  `AgentService._normalize_query_answer` **收敛**（服务端可信对象、状态不推进、
  无执行类工具请求、保留原菜单、四态事实语义与进度边界校正），
  **不允许**任何一条路径自己拼一份只读不变量 —— 两份逻辑各写一遍就会漂移。
- **业务对象的取值来源（v1.20.0 补登）**：问题分析（问题反馈）这一轮的**分析内容**
  仍按**本轮请求里的草稿**计算（用户屏幕上看到的就是它），但**回传的**
  `domainObjects` 取**服务端会话记录**里的可信对象 —— 与咨询路径同源
  （ADR 0002 §1「请求快照不作事实依据」、§4.2「取服务端可信对象」）。
  **分析内容也改走服务端事实**属于改变既有业务输出，本轮**不做**（已知限制登记在
  验收报告 §6）。
- **「指向报表业务对象」按封闭词表的子串匹配判定（v1.20.0 补登）**：
  单字词条（如「图」）**不得**把与报表无关的复合词（图书 / 地图 / 图标 / 图片 /
  蓝图 / 企图）算成业务对象 —— 问「图书有哪几本」不是报表咨询。
- **目录外新增（`OUT_OF_CATALOG_ADD`）不适用「只追加聊天」**（v1.6.0 补登，#65 验收 AC1 缺口后）：
  它**要产出待接受的模拟候选**（`bindingKind = "simulated"`，见 §3.5）。
  意图门**不再**把它挡在确定性编辑快路之外——目录外候选层就长在编辑引擎里
  （`template_edit_engine` → `out_of_catalog_candidate`），挡住快路等于让候选层永远走不到。
  确定性编辑快路是**追加**一次尝试：认不出来就照旧**不产出**，流程落到模型支路。
  **咨询与问题反馈仍然**照旧被挡在快路之前，不受影响。
- 目录外候选**必须**带**可澄清**的问句或**显式假设**；**不静默映射**到已登记指标（规格第 6 条），
  更不伪造 `metricRef`。
- **「别名命中 ≠ 识别成功」**：目录外指标**怎么判定**，见 §3.5。
  意图门放行 ≠ 指标识别成功 —— 目录外候选层**照旧**按 §3.5 的判据走，
  认定「口径对不上」就出候选，认定「确实是那个已登记指标」就走目录内。

### 7.4 澄清额度的清零与保留时点（v1.4.0 补登，#62 实施后提出）

额度**按事项**记（`clarificationKey` = 意图 + 目标卡片），一件事里只问一轮。下表逐个时点写明额度怎么变，
由 `session_service.record_clarification()` / `session_service.reset_clarification()` 落实：

| 时点 | 额度动作 | 为什么 |
| --- | --- | --- |
| 提出了一个**真正抛给用户**的追问 | **轮次 +1**，记到该事项的 key 上 | 只有真的问出去了才算消耗 |
| 追问因工具 / 模型故障**没问成** | **不动**：轮次与 key 都不改 | 技术原因不是用户花的额度 |
| 候选修改计划**落库**（进入待确认） | **不清** | 落库不是新任务，随后的局部调整沿用同一额度 |
| 用户选「**继续调整**」 | **不清** | 仍是同一件事，回到统一对话接着改 |
| 用户选「**取消**」 | **清** | 这件事结束了，下一件事按额度键规则重新开 |
| 修改**被接受并生效** | **清** | 这件事说清了 |
| 普通回复 / 局部调整 | **不清** | 不是新事项 |
| 只读咨询 / 问题反馈 | **不动**：既不计入也不消耗 | 咨询不进入澄清流程 |
| **新事项**（额度 key 变了） | **自然重开**，轮次从 0 起 | `record_clarification` 发现 key 不同即重新计数 |

**清零 = 三键一起清**：`clarificationCount` / `clarificationKey` / `clarificationQuestion`
（`reset_clarification()` 一次性 pop 掉三个）。只清轮次、不清 key **不算清零**——
key 还在，下一次 `record_clarification` 会被判成同一事项而接着累加。

**额度键怎么来（v1.4.1 补登，#58 验收 P1 缺口修复后）**：

- 额度键**由当前这一轮**的「意图 + 目标卡片」推导，**不沿用上一轮的旧键**。
  键变了 → 新事项 → 轮次从 0 起；键没变 → 同一件事 → 轮次接着算，第二轮仍被上限挡住。
- **例外之一**：这一轮认不出意图与目标时（多半是用户在**回答上一轮的追问**），
  **沿用上一轮的键** —— 否则「同一事项续接」会被误判成新事项，白白多问一轮。
  （v1.12.0 修正：原写「**唯一的**例外」，但下面 v1.11.0 又加了第二个例外，正文自相矛盾。）
- 额度用尽时**清掉「上一轮在追问什么」**（`pendingEditRequest` / `pendingEditTimeAnchor`），
  不让它继续缠住新事项。

> 修复前的实现把键钉死在旧键上（`current.key if prior and current`），导致**一轮澄清用完后，
> 用户换任何一件新的修改都会被挡住** —— 与本节「按事项计」直接矛盾。

**「目标由未知变已知」算同一件事（v1.11.0 补登，#66 独立核验后统筹裁定）**：

上面那条例外的**适用范围要放宽一格**。实测有个形状漏了：

1. 第一轮「改成柱状图」（没说改哪一块）→ 系统追问「你想改哪一块？」
2. 第二轮「把能耗趋势改成柱状图」（**把目标补上了**）

第一轮记的额度键是 `CHANGE_VISUALIZATION:`（目标为空），
第二轮键变成 `CHANGE_VISUALIZATION:region_hourly_trend` → 键变了 → 按「键变了 = 新事项」
算成**新事项** → 轮次从 0 起 → **又问了一轮**。
规格第 23 条「一次生成最多被主动问一轮」在这个形状下**守不住**。

**裁定**：**目标由「未知」变成「已知」，是同一事项的延续，不是新事项。**
理由：第二轮是用户在**补全上一轮的追问**，不是提出新要求。

- 口径：**上一轮存在针对同一意图的待澄清追问**，且这一轮把目标补上了
  → 额度键**沿用上一轮的键**，轮次接着算。
- 这**不**放宽「换一件事要能重新追问」：意图变了、或目标换了另一张卡片，
  都是**新事项**，轮次照旧从 0 起。
- 「上一轮在追问什么」的载体就是既有的 `pendingEditRequest` / `pendingEditTimeAnchor`。

**「例外之二」的实现口径（v1.20.0 补登）**：

- 「上一轮存在针对**同一意图**的待澄清追问」= **两个条件同时成立**：
  ① 会话里记着上一轮的额度键（`clarificationKey`），且它的**意图部分**与这一轮
  判出的意图**相同**；② 上一轮**确实抛出过**一个待澄清追问
  （`pendingEditRequest` 仍在）。
  **两个条件缺一不可** —— 只看 ① 会把上一件事的额度错误地套到后来毫不相干的
  一句话上（那正是 v1.4.1 之前的老 bug）。
- 「目标由未知变已知」的判定 = 上一轮键的**目标部分为空**、这一轮的目标**非空**。
  上一轮目标**已知**时换成另一张卡片，仍是**新事项**（轮次从 0 起）。
- 额度键推导**只有一份实现**（`agent_service._derive_clarification_key`），
  不许两处各推一遍 —— 推导规则散开就会漂移。

## 8. 跨概念不变量

1. **候选不覆盖生效**：待确认候选（方案、修改计划、JSON 输入版本）保存但不覆盖生效组合；
   取消、失败、冲突一律保持旧生效组合。
2. **原子切换**：生效组合的切换是**一次**原子提交；模型工作与载荷生成在事务外，
   不持有数据库事务等待模型或网络。
3. **同一份定义、一个来源模式**：一份定义只有一个 `sourceMode`，不混两种来源的数字。
4. **模拟数值不落盘**：模拟业务数值只在响应与内存；**用户提供的 JSON 原始数据是例外**
   （见 §4.3 与 ADR 0004 §8）。
5. **描述驱动，不猜**：模拟字段的语义类别与值形态来自 `previewSpec` 描述，
   **不按标题 / 列名猜**（ADR 0004 §5.4）。
6. **锁只是引导**：界面锁定不构成安全边界；后端对确认与权限的校验才是边界。
7. **诊断不改行为**：诊断与元信息采集不改变模型提示词、解析与重试。
8. **说的和做的一致**：关于「这批数字是什么」的每一句说明，都必须与**实际执行的处理**一致 ——
   不许拿第一行冒充指标值、不许写「按求和展示」而实际没求和、不许按列名猜轴（§4.3.1）。
   **宁可少说，不许说假话。**
9. **同一句话只说一次**：整份报表层面的问题（`metadata.jsonInputIssues`）**只在面板顶部出现一次**，
   **不重复**进每个区域的说明；区域说明只讲区域自己的事。
   前端逐字渲染服务端写好的说明，**不改写、不总结、不重排**（§4.3.2）。
